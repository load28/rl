# 설계 제안: 파이프라인 연산자 `|>`

- **상태**: 제안 (구현 전 — 승인 시 구현 태스크를 별도 등록)
- **태스크**: [TASK-013](../tasks/TASK-013-pipeline-operator-proposal.md)

## 1. 목표

rl에 **파이프 기반 함수형 체이닝**을 추가한다. 요구사항은 네 가지다:

1. **타입 추론이 정확해야 한다** — 입력, 출력, 그리고 체인의 **모든 중간
   단계**에서 tsc의 추론이 온전히 동작해야 한다.
2. **컴파일 결과는 순수 TypeScript**여야 한다 — 런타임 주입 없음, 타입 트릭
   없음 (기존 설계 계약 그대로).
3. **Rust처럼 읽혀야 한다** — 데이터가 왼쪽에서 오른쪽으로 흐르는 체이닝.
4. **Ramda처럼 동작해야 한다** — 단항 함수(data-last, 커링)를 이어 붙이는
   포인트프리 합성.

## 2. 왜 라이브러리 함수(`pipe(...)`)가 아니라 연산자인가

Ramda 스타일 `pipe(f, g, h)(x)`를 std 함수로 제공하는 방법부터 검토했다.
그러나 TypeScript에서 가변 인자 `pipe`의 타입은 **고정 arity 오버로드**로만
표현할 수 있고, 두 가지 고질적 추론 문제가 있다:

- 오버로드 개수(보통 7~10개)를 넘는 체인은 타입을 잃는다.
- **제네릭 함수를 합성하면 타입 파라미터가 구체화되지 못하고 `unknown`으로
  붕괴한다** (TS의 오래된 한계 — 고차 함수 합성 시 제네릭 추론 불가).
  Ramda/lodash-fp 사용자가 겪는 바로 그 문제다.

즉 "각 체이닝 단계에서 정확한 타입 추론"이라는 요구는 **라이브러리 타입으로는
원천적으로 달성할 수 없다.** 반면 연산자를 컴파일 시점에 **단계별 직접 함수
적용으로 디슈가**하면, 생성물은 평범한 함수 호출의 나열이 되고 tsc는 각 호출을
독립적으로 — 제네릭 포함 — 완전하게 추론한다. arity 한계도 없다.

이것은 rl의 기존 설계 계약과도 정확히 맞는다: **rlc는 타입 추론을 전혀 하지
않는다.** 구조만 변환하고 타입은 전부 tsc에 맡긴다 (에러 계층 분리 계약).

## 3. 문법

```
파이프라인 ::= head ("|>" step)+
head       ::= 식                    // 임의의 TypeScript 표현식
step       ::= 식                    // 단항 함수로 평가되는 임의의 표현식
```

```rl
const total = ["1", "2", "3"]
  |> (xs => xs.map(Number))
  |> (ns => ns.reduce((a, b) => a + b, 0));
```

### 3.1 의미: F# 스타일 적용

`x |> f`는 `f(x)`다. step은 **단항 함수로 평가되는 식**이고, 파이프는 왼쪽
값을 그 함수에 적용한다. 인자가 더 필요하면 커링된 함수를 호출해 단항 함수를
얻거나(`x |> add(2)` — Ramda 방식), 화살표 함수를 쓴다(`x |> (n => f(n, 2))`).

파이프라인은 **표현식**이다. `match`처럼 인자 위치, 템플릿 보간, match 암 본문
등 표현식이 오는 어디에나 쓸 수 있다.

### 3.2 왜 Hack 스타일(topic 토큰)이 아닌가

TC39에서 경쟁했던 두 방식을 모두 검토했다:

| | F# 스타일 (제안) | Hack 스타일 |
|---|---|---|
| 형태 | `x \|> f` → `f(x)` | `x \|> f(%, 2)` → `f(x, 2)` |
| 파싱 | `\|>`로 **분리만** 하면 됨 | step 식 **내부**에서 topic 토큰(`%`)을 찾아야 함 |
| rl 파서와의 정합 | 바이트 단위 구조 파싱으로 충분 | 식 수준 파싱 필요 — `%`가 topic인지 나머지 연산인지 는 연산자/피연산자 위치를 알아야 구분됨 |
| Ramda 정합 | data-last 커링과 그대로 일치 | 커링 불필요, 그러나 Ramda 관용구와 다름 |

rl 파서는 의도적으로 **오류 없는 바이트 단위 구조 파서**다(설계 문서
[compiler-architecture.md](./compiler-architecture.md)). Hack 스타일의 topic
토큰은 step 식을 실제 표현식 문법으로 파싱해야만 안전하게 찾을 수 있어 이
아키텍처와 충돌한다. F# 스타일은 최상위 `|>` 분리만으로 완결되고, "Ramda처럼
동작"이라는 목표와도 정확히 일치하므로 F# 스타일을 선택한다.

### 3.3 통과 계약 안전성

`|>`(`|` 바로 뒤 `>`)는 **유효한 TypeScript 어디에도 등장할 수 없는 토큰
열이다.** `|`는 이항 연산자(비트 OR / 유니언 타입)라서 뒤에 피연산자(식 또는
타입)가 와야 하는데, `>`는 식도 타입도 시작할 수 없기 때문이다. 문자열, 주석,
정규식, 템플릿 리터럴 텍스트 안의 `|>`는 기존 스캐너가 이미 건너뛴다.

따라서 `|>`를 rl 구문으로 클레임해도 **"모든 유효한 TS 파일은 유효한 .rl
파일"** 계약은 깨지지 않는다 — `enum`/`match`/`try`와 달리 오인 가능한 유효 TS
형태 자체가 존재하지 않는다.

## 4. 컴파일 결과

match의 선례(switch IIFE)를 따라 **단계별 const를 가진 화살표 IIFE**로
방출한다:

입력:

```rl
const total = ["1", "2"] |> (xs => xs.map(Number)) |> sum;
```

출력 (형태):

```ts
const total = ((() => {
  const $rl_p0 = (["1", "2"]);
  const $rl_p1 = ((xs => xs.map(Number)))($rl_p0);
  return ((sum))($rl_p1);
})());
```

- 임시 변수는 `try`와 같은 방식으로 파일 단위 유일(`$rl_p0`, `$rl_p1`, ...).
- head와 각 step 식은 **원문 그대로**(재귀 파싱된 rl 구문만 변환) 괄호에 싸여
  들어간다 — 사용자 코드의 타입 에러는 사용자 텍스트 위에서 tsc가 보고한다.
- head/step에 `await`가 있으면 match §3.5와 동일하게 async IIFE + 전체
  `await`로 방출한다 (감지도 동일하게 토큰 단위).

### 4.1 왜 중첩 호출이 아니라 IIFE인가

`(sum)(((xs => ...))((["1","2"])))` 같은 **중첩 호출** 방출도 검토했다. 더
짧지만 결정적 결함이 있다: JS는 호출식에서 **callee를 인자보다 먼저** 평가하므로
중첩 호출은 step 식들을 오른쪽부터 평가한다. 파이프라인의 직관(그리고 Rust
체이닝의 의미)은 **head → step1 → step2 순서**다. IIFE + const 방출은:

- 평가 순서가 정확히 좌→우다.
- 각 중간 값이 `const $rl_pN`으로 물질화되어 **단계별 타입이 생성물에서 그대로
  드러난다** — "각 체이닝 단계의 정확한 추론" 요구가 tsc 수준에서 검증 가능한
  형태로 남는다.
- 디버거에서 단계별 값을 관찰할 수 있다.

### 4.2 타입 추론이 정확한 이유

생성물이 평범한 단항 함수 적용의 나열이므로:

- **입력**: `$rl_p0`의 타입 = head 식의 추론 타입.
- **각 단계**: `$rl_pN`의 타입 = 해당 step 함수의 반환 타입. step이 제네릭
  함수여도 **실제 인자에 대해 호출되므로** 타입 파라미터가 정상적으로
  구체화된다 (`pipe()` 합성과 달리 고차 추론이 필요 없다).
- **출력**: IIFE 반환 타입으로 자연 추론.
- step이 단항 함수가 아니면(인자 타입 불일치, 함수 아님) tsc가 해당 step
  텍스트 위치에서 표준 에러로 보고한다.

rlc는 아무 타입 판단도 하지 않는다 — 에러 계층 분리 계약 유지.

## 5. 구조 파싱 규칙

파서는 지금처럼 오류 없이, **완전하게 파싱될 때만** 클레임한다.

- **트리거**: 최상위 스캔에서 `|>`(직전 바이트가 `|`가 아닌 것) 발견.
- **head**: 스캔 루프가 최상위 구분자(`;` `,` `(` `[` `{` `}` `=`(단 `=>`
  제외) `return` 등 식 경계)를 지날 때마다 "현재 식 시작" 오프셋을 갱신해
  두었다가, `|>`를 만나면 그 오프셋부터 `|>` 직전까지를 head로 잡는다. head가
  이미 세그먼트로 분리된 rl 구문(템플릿, match)을 포함하면 스팬 기준으로
  되감아 head의 하위 Program으로 흡수한다.
- **step**: `|>` 다음부터 다음 최상위 `|>` 또는 식 종결자(`;` `,` `)` `]`
  `}`)까지. head와 step은 재귀 파싱(Program)되므로 내부의 match/enum/템플릿/
  중첩 파이프라인이 모두 동작한다.
- **삼항 `? :`와 괄호 없는 화살표 함수는 head/step 최상위에서 허용하지
  않는다** — 괄호로 감싼다(`x |> (c ? f : g)`, `x |> (n => n + 1)`). 우선순위
  모호성을 규범으로 제거하고 구조 파싱을 단순하게 유지하기 위한 규칙이다
  (match의 "스크루티니 괄호 필수", 표현식 암의 "객체 리터럴 괄호 필수"와 같은
  성격).

### 5.1 에러 계층 (sema)

`|>`는 유효 TS에 존재할 수 없으므로, **구조 파싱에 실패해 verbatim으로 남은
`|>`는 조용히 통과시키지 않고 sema가 `파일:행:열`과 함께 rl 에러로 보고한다**
(통과시키면 생성물이 유효하지 않은 TS가 되어 출력 자가 검사에서 위치 정보 없이
실패하게 된다 — 에러 계층 계약 위반). 추가 sema 검사:

- 빈 step (`x |> |> f`, `x |>;`) — 구조 파싱 실패 → 위 에러로 수렴.
- step/head 내부의 `try` 문 — match와 동일한 사유로 금지 (§5.4의 IIFE
  `return` 의미 변화).

`errors.md`에 추가할 메시지 (형태):

```
rlc: file.rl:3:9: "|>" pipeline could not be parsed here
     (steps must be expressions; parenthesize ternaries and arrow functions)
```

### 5.2 기존 구문과의 상호작용

- **`try` 식 내부**: `const a = try readCfg() |> normalize;` — try의 식은
  이미 재귀 파싱되므로(`tries.rs`가 `parse_range`로 위임) 자연스럽게
  합성된다. try의 식 스캐너(`scan_stmt_expr_end`)는 `|`/`>`에서 중단하지
  않으므로 추가 작업이 거의 없다.
- **match와**: 스크루티니(`match (x |> f) { ... }`)와 암 본문 모두 재귀
  파싱이라 자동 지원.
- **템플릿 보간 내부**: `` `${x |> f}` `` — 보간이 재귀 Program이므로 자동
  지원.

## 6. AST / 단계별 변경 범위

기존 파이프라인 규범(새 구문 = ast + parser + codegen, 새 검사 = sema)대로:

```rust
// ast.rs
Segment::Pipe(PipeExpr)

pub(crate) struct PipeExpr {
    pub head_span: Span,      // await 감지·에러 보고용
    pub head: Program,        // 재귀 파싱
    pub steps: Vec<PipeStep>,
}
pub(crate) struct PipeStep {
    pub span: Span,
    pub body: Program,
}
```

- `parser/pipes.rs` (신규): §5의 구조 파싱.
- `sema.rs`: verbatim 구간의 스트레이 `|>` 검출, step 내 `try` 금지.
- `codegen/pipes.rs` (신규): §4의 IIFE 방출, `$rl_pN` 카운터.
- `verify.rs`: 변경 없음 (출력 자가 검사가 그대로 안전망).

## 7. 표준 라이브러리 (후속 단계)

현재 std 콤비네이터는 data-first다: `Option.map(o, f)`. 파이프에 그대로 넣을
수 없고 화살표로 감싸야 한다:

```rl
half(4) |> (o => Option.map(o, x => x + 1)) |> (o => Option.unwrapOr(o, 0))
```

**후속 태스크**로 data-last 커링 변형을 std에 추가하면 Ramda/Rust 관용구가
완성된다:

```rl
half(4) |> Option.mapP(x => x + 1) |> Option.unwrapOrP(0)
```

- 커링 변형은 순수 TS 한 줄씩이다: `mapP: <T, U>(f: (v: T) => U) =>
  (o: Option<T>): Option<U> => ...` — 단항 함수를 반환하므로 파이프 추론과
  정확히 맞물린다.
- 네이밍(`mapP` 접미사 vs 별도 네임스페이스 vs 기존 API를 data-last로 교체)은
  기존 사용자 호환성이 걸린 결정이라 **개방 질문**으로 남긴다. 연산자 자체는
  std 변경 없이도 완결적으로 동작하므로 단계를 분리한다.

## 8. 테스트 계획 (세 계층)

- **compile.rs**: 기본 2단계/다단계 스냅샷, 제네릭 함수 step, 중첩
  파이프라인, match 스크루티니·암 본문 내 파이프, `try ... |> ...;`, await
  포함(async IIFE), 스트레이 `|>` 에러, step 내 `try` 에러.
- **passthrough.rs**: `a | b`, `a || b`, `a | b > c`, 유니언 타입 `A | B`,
  문자열 `"a |> b"`·주석·정규식·템플릿 텍스트 안의 `|>` — 전부 바이트 그대로.
- **integration.rs**: tsc 타입체크로 단계별 추론 검증(제네릭 step이 구체화되는
  케이스 포함 — `pipe()` 라이브러리가 실패하는 바로 그 형태), node 실행으로
  평가 순서(좌→우)와 값 검증.
