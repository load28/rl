  [`std.md`](../reference/std.md#파이프라인-변형-p)
- **태스크**: [TASK-013](../tasks/TASK-013-pipeline-operator-proposal.md) (제안),
  [TASK-043](../tasks/TASK-043-pipeline-operator-impl.md) (구현),
  [TASK-063](../tasks/TASK-063-flow-composition.md) (`flow` 합성)

## 1. 목표

rl에 **파이프 기반 함수형 체이닝**을 추가한다. 요구사항은 네 가지다:

1. **타입 추론이 정확해야 한다** — 입력, 출력, 그리고 체인의 **모든 중간
   단계**에서 tsc의 추론이 온전히 동작해야 한다. 스텝 안의 화살표 함수
   파라미터까지 주석 없이 추론되어야 한다.
2. **컴파일 결과는 순수 TypeScript**여야 한다 — 런타임 주입 없음, 타입 트릭
   없음 (기존 설계 계약 그대로).
3. **Rust처럼 읽혀야 한다** — 데이터가 왼쪽에서 오른쪽으로 흐르는 체이닝
   (메서드 체이닝 포함).
4. **Ramda처럼 동작해야 한다** — 단항 함수(data-last, 커링)를 이어 붙이는
   포인트프리 합성.

목표 사용감:

```rl
import type { TOption } from "@rl/std";
import * as Option from "@rl/std/option";

const label = half(4)
  |> Option.mapP(x => x + 1)
  |> Option.unwrapOrP(0)
  |> .toFixed(1);
```

## 2. 왜 라이브러리 함수(`pipe(...)`)가 아니라 연산자인가

Ramda 스타일 `pipe(f, g, h)(x)`를 std 함수로 제공하는 방법부터 검토했다.
그러나 TypeScript에서 가변 인자 `pipe`의 타입은 **고정 arity 오버로드**로만
표현할 수 있고, 두 가지 고질적 추론 문제가 있다:

- 오버로드 개수(보통 7~10개)를 넘는 체인은 타입을 잃는다.
- **제네릭 함수를 합성하면 타입 파라미터가 구체화되지 못하고 `unknown`으로
  붕괴한다** (TS의 오래된 한계 — 고차 함수 합성 시 제네릭 추론 불가).
  Ramda/lodash-fp 사용자가 겪는 바로 그 문제다.

즉 "각 체이닝 단계에서 정확한 타입 추론"이라는 요구는 **라이브러리 타입으로는
원천적으로 달성할 수 없다.** 반면 연산자를 컴파일 시점에 단계별 적용으로
디슈가하면, 생성물은 평범한 함수 호출의 나열이 되고 tsc는 각 호출을
독립적으로 — 제네릭 포함 — 완전하게 추론한다. arity 한계도 없다.

이것은 rl의 기존 설계 계약과도 정확히 맞는다: **rlc는 타입 추론을 전혀 하지
않는다.** 구조만 변환하고 타입은 전부 tsc에 맡긴다 (에러 계층 분리 계약).

## 3. 문법

```
파이프라인 ::= head ("|>" step)+
head       ::= 식                     // 임의의 TypeScript 표현식
step       ::= 식                     // 적용 스텝: 단항 함수로 평가되는 식
             | "." 포스트픽스-체인    // 메서드 스텝: 파이프 값에 대한 체인
```

### 3.1 적용 스텝: F# 스타일

`x |> f`는 `f(x)`다. step은 **단항 함수로 평가되는 식**이고, 파이프는 왼쪽
값을 그 함수에 적용한다. 인자가 더 필요하면 커링된 함수를 호출해 단항 함수를
얻거나(`x |> add(2)` — Ramda 방식, std의 `*P` 콤비네이터 — §7), 화살표
함수를 쓴다(`x |> (n => f(n, 2))`).

### 3.2 메서드 스텝: `.`으로 시작하는 step

step이 `.` + 식별자로 시작하면 **파이프 값에 대한 포스트픽스 체인**이다:

```rl
const total = csv |> .trim() |> .split(",") |> .map(Number) |> sum;
```

- `x |> .m(a)`는 `(x).m(a)`, `x |> .p`는 `(x).p`다. 한 스텝 안에서 체인을
  이어도 된다: `x |> .trim().split(",")`.
- 네이티브 메서드(문자열/배열/Promise 등)를 화살표 래핑 없이 파이프에 끼워
  넣기 위한 형태로, Rust의 `.map().filter()` 체이닝 감각을 그대로 제공한다.
- `|>` 다음의 `.`은 유효 TS에 존재할 수 없는 위치이고, step의 첫 유의
  바이트만 보면 판별되므로 바이트 단위 구조 파싱과 완전히 호환된다.
  (Hack 스타일 topic처럼 step 내부를 식 문법으로 파싱할 필요가 없다.)
- `?.` 시작은 1차 범위에서 제외한다 (향후 확장 여지).

파이프라인은 **표현식**이다. `match`처럼 인자 위치, 템플릿 보간, match 암
본문 등 표현식이 오는 어디에나 쓸 수 있다.

### 3.3 왜 Hack 스타일(topic 토큰)이 아닌가

TC39에서 경쟁했던 두 방식을 모두 검토했다:

| | F# 스타일 (제안) | Hack 스타일 |
|---|---|---|
| 형태 | `x \|> f` → `f(x)` | `x \|> f(%, 2)` → `f(x, 2)` |
| 파싱 | `\|>`로 **분리만** 하면 됨 | step 식 **내부**에서 topic 토큰(`%`)을 찾아야 함 |
| rl 파서와의 정합 | 바이트 단위 구조 파싱으로 충분 | 식 수준 파싱 필요 — `%`가 topic인지 나머지 연산인지는 연산자/피연산자 위치를 알아야 구분됨 |
| Ramda 정합 | data-last 커링과 그대로 일치 | 커링 불필요, 그러나 Ramda 관용구와 다름 |

rl 파서는 의도적으로 **오류 없는 바이트 단위 구조 파서**다(설계 문서
[compiler-architecture.md](./compiler-architecture.md)). Hack 스타일의 topic
토큰은 step 식을 실제 표현식 문법으로 파싱해야만 안전하게 찾을 수 있어 이
아키텍처와 충돌한다. F# 스타일은 최상위 `|>` 분리만으로 파싱이 완결되고,
"Ramda처럼 동작" 요구와도 정확히 일치한다. Hack 스타일의 실용적 장점(임의
인자 위치, 메서드 호출)은 메서드 스텝(§3.2)과 커링 std(§7)가 흡수한다.

### 3.4 통과 계약 안전성

`|>`(`|` 바로 뒤 `>`)는 **유효한 TypeScript 어디에도 등장할 수 없는 토큰
열이다.** `|`는 이항 연산자(비트 OR / 유니언 타입)라서 뒤에 피연산자(식 또는
타입)가 와야 하는데, `>`는 식도 타입도 시작할 수 없기 때문이다. 문자열, 주석,
정규식, 템플릿 리터럴 텍스트 안의 `|>`는 기존 스캐너가 이미 건너뛴다.

따라서 `|>`를 rl 구문으로 클레임해도 **"모든 유효한 TS 파일은 유효한 .rl
파일"** 계약은 깨지지 않는다 — `enum`/`match`/`try`와 달리 오인 가능한 유효 TS
형태 자체가 존재하지 않는다.

## 4. 컴파일 결과

파이프라인이 하나라도 있는 파일에는 **2인자 적용 헬퍼**를 파일당 한 번
방출하고, 각 적용 스텝을 그 헬퍼 호출로 중첩한다. 메서드 스텝은 포스트픽스를
그대로 잇는다:

입력:

```rl
const label = half(4)
  |> Option.mapP(x => x + 1)
  |> Option.unwrapOrP(0)
  |> .toFixed(1);
```

출력 (형태):

```ts
const $rl_ap = <A, B>(v: A, f: (v: A) => B): B => f(v);   // 파일당 1회

const label = ($rl_ap($rl_ap((half(4)),
  (Option.mapP(x => x + 1))), (Option.unwrapOrP(0)))).toFixed(1);
```

- 헬퍼는 순수 TypeScript 5줄짜리 제네릭 화살표 const다 — 런타임 주입이
  아니라 match의 IIFE, try의 `$rl_t0` 임시 변수와 같은 성격의 생성물이며,
  이름은 기존 `$rl_` 접두 규약을 따른다.
- head와 각 step 식은 **원문 그대로**(재귀 파싱된 rl 구문만 변환) 괄호에
  싸여 들어간다 — 사용자 코드의 타입 에러는 사용자 텍스트 위에서 tsc가
  보고한다.

### 4.1 방출 형태의 결정 근거 (tsc로 검증)

세 가지 방출 후보를 실제 tsc(`--strict --noEmit`)로 검증했다:

| 후보 | 커링 스텝 추론 | 평가 순서 | await |
|------|---------------|-----------|-------|
| (A) 직접 적용 중첩 `(step)(prev)` | **실패** — `x: unknown` | 우→좌 (callee 먼저) | 동작 |
| (B) IIFE + 단계별 const + 직접 적용 | **실패** — (A)와 동일 | 좌→우 | async 감지 필요 |
| (C) `$rl_ap` 헬퍼 중첩 (선택) | **성공** | 좌→우 | IIFE가 없어 자연 동작 |

핵심은 TypeScript의 추론 방향이다. `Option.mapP(x => x + 1)`처럼 **커링
콤비네이터를 데이터 없이 먼저 호출하면**, 그 호출 시점에는 `T`를 알 수 없어
`x`가 `unknown`으로 붕괴한다(F#의 Hindley-Milner와 달리 TS는 역방향 유추를
하지 않는다). 이 실패는 (A)·(B) 형태 모두에서 재현된다 — **callee 위치는
문맥 타입을 받지 못하기 때문이다.**

반면 (C)는 step을 `$rl_ap`의 **인자 위치**에 두므로, 파라미터 타입
`(v: A) => B`가 문맥 타입이 되어 **반환 타입 문맥 추론**(fp-ts `pipe`가
동작하는 바로 그 메커니즘)이 작동한다: `A = TOption<number>`가 먼저 고정되고,
지연 검사되는 화살표의 `x`가 `number`로 추론된다. 부수 효과로 두 문제가 함께
풀린다:

- **평가 순서**: `$rl_ap($rl_ap(h, s1), s2)`는 JS 인자 평가 규칙에 따라
  `h → s1 → s2` 순서로 평가된다 — 직접 적용 중첩 `s2(s1(h))`가 callee를
  먼저 평가해 우→좌가 되는 문제가 없다. Rust 체이닝의 의미와 일치한다.
- **await**: IIFE가 없으므로 head/step 안의 `await`가 둘러싼 async 컨텍스트
  에서 그대로 동작한다. match §3.5의 토큰 단위 async 감지 휴리스틱과 그
  제한사항이 파이프라인에는 아예 필요 없다.

(검증 스크립트: 커링 콤비네이터 표준/헬퍼 적용, 메서드 스텝, 제네릭 사용자
함수 통과, head의 await — 구현 태스크에서 integration.rs로 이관한다.)

### 4.2 타입 추론이 정확한 이유

- **입력**: 안쪽 `$rl_ap`의 `A` = head 식의 추론 타입.
- **각 단계**: 단계 n의 값 타입 = `$rl_ap` 반환 타입 `B` — step 함수의 실제
  반환 타입으로 구체화된다. step이 제네릭 함수여도 값 인자와 문맥 타입이
  모두 있으므로 정상 구체화된다 (`pipe()` 라이브러리 합성과 달리 고차 추론이
  필요 없다). 메서드 스텝은 평범한 멤버 접근이라 자명하다.
- **출력**: 가장 바깥 호출의 반환 타입으로 자연 추론.
- step이 단항 함수가 아니면(인자 타입 불일치, 함수 아님) tsc가 해당 step
  텍스트 위치에서 표준 에러로 보고한다.

rlc는 아무 타입 판단도 하지 않는다 — 에러 계층 분리 계약 유지.

## 5. 구조 파싱 규칙

파서는 지금처럼 오류 없이, **완전하게 파싱될 때만** 클레임한다.

- **트리거**: 최상위 스캔에서 `|>`(직전 바이트가 `|`가 아닌 것) 발견.
- **head**: 스캔 루프가 최상위 구분자(`;` `,` `(` `[` `{` `}` `=`(단 `=>`
  제외) `return` 등 식 경계)를 지날 때마다 "현재 식 시작" 오프셋을 갱신해
  두었다가, `|>`를 만나면 그 오프셋부터 `|>` 직전까지를 head로 잡는다. head가
  이미 세그먼트로 분리된 rl 구문(템플릿, match)을 포함하면 스팬 기준으로
  되감아 head의 하위 Program으로 흡수한다.
- **step**: `|>` 다음부터 다음 최상위 `|>` 또는 식 종결자(`;` `,` `)` `]`
  `}`)까지. 첫 유의 바이트가 `.`이고 그다음이 식별자 시작이면 메서드 스텝,
  아니면 적용 스텝이다. head와 step은 재귀 파싱(Program)되므로 내부의
  match/enum/템플릿/중첩 파이프라인이 모두 동작한다.
- **삼항 `? :`와 괄호 없는 화살표 함수는 head/step 최상위에서 허용하지
  않는다** — 괄호로 감싼다(`x |> (c ? f : g)`, `x |> (n => n + 1)`). 우선순위
  모호성을 규범으로 제거하고 구조 파싱을 단순하게 유지하기 위한 규칙이다
  (match의 "스크루티니 괄호 필수", 표현식 암의 "객체 리터럴 괄호 필수"와 같은
  성격).

### 5.1 에러 계층 (sema)

`|>`는 유효 TS에 존재할 수 없으므로, **구조 파싱에 실패해 verbatim으로 남은
`|>`는 조용히 통과시키지 않고 sema가 `파일:행:열`과 함께 rl 에러로 보고한다**
(통과시키면 생성물이 유효하지 않은 TS가 되어 출력 자가 검사에서 위치 정보 없이
실패하게 된다 — 에러 계층 계약 위반). 추가 sema 검사:

- 빈 step (`x |> |> f`, `x |>;`), 식별자가 따라오지 않는 `.` 스텝 — 구조
  파싱 실패 → 위 에러로 수렴.
- step/head 내부의 `try` 문 — match와 동일한 사유로 금지 (§5.4의 `return`
  의미 변화).

`errors.md`에 추가할 메시지 (형태):

```
rlc: file.rl:3:9: "|>" pipeline could not be parsed here
     (steps must be expressions; parenthesize ternaries and arrow functions)
```

### 5.2 기존 구문과의 상호작용

- **`try` 식 내부**: `const a = try readCfg() |> normalize;` — try의 식은
  이미 재귀 파싱되므로(`tries.rs`가 `parse_range`로 위임) 자연스럽게
  합성된다. try의 식 스캐너(`scan_stmt_expr_end`)는 `|`/`>`에서 중단하지
  않으므로 추가 작업이 거의 없다.
- **match와**: 스크루티니(`match (x |> f) { ... }`)와 암 본문 모두 재귀
  파싱이라 자동 지원.
- **템플릿 보간 내부**: `` `${x |> f}` `` — 보간이 재귀 Program이므로 자동
  지원.

## 6. AST / 단계별 변경 범위

## 7. 표준 라이브러리: data-last 커링 콤비네이터 (동시 도입)

현재 std 콤비네이터는 data-first다: `Option.map(o, f)`. 파이프에 그대로 넣을
수 없고 화살표로 감싸야 하므로, **연산자와 같은 단계에서** data-last 커링
변형을 추가한다. F#이 화살표 없는 파이프라인을 쓸 수 있는 이유가 "모든
함수가 커링 + data-last"라는 표준 라이브러리 형태이듯, 이 변형이 있어야
연산자가 관용적으로 쓰인다:

```rl
half(4) |> Option.mapP(x => x + 1) |> Option.unwrapOrP(0)
```

- **네이밍: 기존 객체에 `P` 접미사 변형을 추가한다** (`mapP`, `andThenP`,
  ...). 기존 data-first API는 그대로 유지되어 호환성이 깨지지 않고, 추가
  import 없이 같은 `Option`/`Result` 객체에서 발견된다. 검토한 대안 —
  별도 네임스페이스(`OptionP.map`): import 이중화; data-last로 API 교체:
  기존 사용자 파손 — 은 기각.
- 추가 목록: `Option.mapP/andThenP/orElseP/filterP/unwrapOrP/unwrapOrElseP/`
  `expectP/okOrP`, `Result.mapP/mapErrP/andThenP/orElseP/unwrapOrP/`
  `unwrapOrElseP/expectP`. 각각 순수 TS 한 줄 커링이다:
  `mapP: <T, U>(f: (v: T) => U) => (o: TOption<T>): TOption<U> => ...`.
- **이미 단항인 멤버는 변형이 필요 없다** — `Option.isSome/isNone/toNullable`,
  `Result.isOk/isErr/ok/err`는 지금 그대로 파이프에 들어간다:
  `r |> Result.ok |> Option.toNullable`.
- 커링 변형의 화살표 인자 추론은 §4.1의 헬퍼 방출이 보장한다 (tsc 검증
  완료 — 방출 형태가 직접 적용이었다면 이 API는 전부 `unknown` 붕괴로
  무용지물이 됐다).

### 7.1 왜 Option에 "진짜 메서드"를 달지 않는가

Rust처럼 `opt.map(f).unwrapOr(0)` 하려면 값이 메서드를 가진 클래스
인스턴스여야 한다. 그러나 std의 `Option`/`Result` 값은 **rl enum 컴파일
결과와 정확히 같은 형태의 순수 태그드 유니언**이라는 계약(stdlib 계약
테스트가 바이트 일치로 강제)이 있고, 클래스화하면 직렬화(JSON), 구조적
동등성, `match`와의 형태 일치가 전부 깨진다. 메서드 스텝 + 커링 std가 같은
체감을 순수 데이터 위에서 제공하므로 클래스화는 하지 않는다:

```rl
// Rust:  half(4).map(|x| x + 1).unwrap_or(0).to_string()
half(4) |> Option.mapP(x => x + 1) |> Option.unwrapOrP(0) |> .toString()
```

## 11. `flow` — 값 없는 합성 (TASK-063)

파이프는 **값**을 함수들에 흘려보낸다. 같은 체인을 **값 없이** 조립해 함수를
만드는 형태가 `flow`다 (`flow |> f |> g` = "f 다음 g"인 함수).

### 11.1 문법: 왜 head 자리의 `flow`인가

| 후보 | 형태 | 평가 |
|------|------|------|
| (A) head 없는 파이프라인 | `\|> f \|> g` | 유효 TS에 없는 형태라 계약은 안전하지만, head를 **빠뜨린 오타**가 조용히 "값 파이프 → 함수 값"으로 의미를 바꾼다. 여러 줄 파이프라인이 이미 `\|>`로 줄을 시작하므로 눈으로도 구분이 어렵다 |
| (B) 라이브러리 `flow(f, g)` | `flow(f, g)` | 오버로드 arity 한계 + 고차 제네릭 붕괴 — §2에서 파이프를 연산자로 만든 이유가 그대로 재현된다 |
| (C) 합성 연산자 | `f >> g` | `>>`는 유효 TS의 시프트 연산자 — **통과 계약 위반**. 불가 |
| (D) head 자리의 `flow` (선택) | `flow \|> f \|> g` | 값이 놓일 자리에 이름이 놓이므로 파이프와 형태가 1:1로 대응하고, 파서는 "head 토큰이 `flow` 하나인가"만 보면 된다. head를 빠뜨리면 (A)와 달리 기존 에러로 걸린다 |

(D)를 선택했다. `flow`는 **문맥 키워드**다 — head가 정확히 식별자 `flow`
하나일 때만 합성이고, 그 외의 `flow`(import된 fp-ts `flow`, 변수, 속성,
호출)는 평범한 TS 식별자다. `flow`라는 변수를 파이프에 흘리려면 괄호로
감싼다(`(flow) |> f`) — match 스크루티니 괄호와 같은 성격의 규범이다.
통과 계약은 영향을 받지 않는다: 합성으로 클레임되는 코드에는 반드시 `|>`가
있고, `|>`가 있는 파일은 애초에 유효한 TS가 아니다.

### 11.2 방출 형태: 이항 합성 헬퍼의 중첩

```ts
function $rl_fl<A extends unknown[], B, C>(f: (...a: A) => B, g: (b: B) => C): (...a: A) => C { return (...a: A) => g(f(...a)); }
```

`flow |> f |> g |> h` → `$rl_fl($rl_fl((f), (g)), (h))`.

검토한 대안과 tsc(`--strict`) 검증 결과:

| 후보 | 결과 |
|------|------|
| (A) 화살표 방출 `($rl_v) => $rl_ap($rl_ap($rl_v, f), g)` | **탈락** — 파라미터에 문맥 타입이 없어 `noImplicitAny`에서 TS7006. rlc가 방출한 코드가 tsc 에러를 내므로 **에러 계층 계약 위반** |
| (B) 가변 인자 `flow(...fns)` 헬퍼 | **탈락** — 오버로드 arity 한계·중간 단계 타입 소실 (라이브러리 `flow`과 동일) |
| (C) 이항 `$rl_fl` 중첩 (선택) | **성공** — arity 한계 없음, 각 호출이 앞 스텝의 반환 타입에서 구체적으로 추론, `A extends unknown[]`로 첫 스텝의 **다인자 arity 보존** |

메서드 스텝은 헬퍼의 인자 위치에 놓이는 화살표로 방출한다
(`$rl_fl(prev, (($rl_v) => ($rl_v).toFixed(1)))`) — 그 자리에서 파라미터
타입 `(b: B) => C`가 문맥이 되므로 `$rl_v`는 암묵적 `any`가 되지 않는다.
**첫 스텝**에는 그 문맥이 없으므로 메서드 스텝을 금지하고 sema가 위치와 함께
보고한다.

### 11.3 입력 타입의 한계 (의도적)

값이 없으므로 입력 타입은 **첫 스텝의 파라미터 타입**이다. 첫 스텝이 제네릭
함수거나 커링 콤비네이터면 추론할 근거가 없어 `unknown`으로 붕괴한다 — TS가
고차 위치의 제네릭을 추론하지 못하는 한계로, fp-ts `flow`도 동일하다. 해법은
타입 인자를 직접 주는 것(`flow |> wrap<number> |> ...`)이고, 이는 규범
문서에 한계로 명시한다. 두 번째 스텝부터는 파이프와 똑같이 문맥 추론이
동작한다 (§4.1의 메커니즘 그대로).
