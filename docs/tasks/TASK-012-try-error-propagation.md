## 목적

TASK-011의 `Result` 위에서 Rust의 `?` 연산자처럼 에러를 **값으로 리턴하며
전파**하는 구문을 제공한다. 실패 시 조기 리턴을 콤비네이터 체이닝 없이
직선적인 코드로 쓸 수 있게 한다.

## 범위

- 포함:
  - 새 구문 `try` 문 두 형태 (모두 `;` 필수):
    - `const|let|var <바인딩> = try <식>;`
    - `try <식>;` (값을 버리고 전파만)
  - 방출: 함수 스코프의 문장 3개(임시 const → Err면 return → 값 언랩)를
    한 줄로. IIFE 없음 — `await`가 식 안에 있어도 그대로 동작.
  - sema: match 표현식·템플릿 보간·다른 try 식 내부의 try는 명확한 컴파일
    에러 (IIFE 경계 때문에 `return` 의미가 달라지는 위치).
  - 세 계층 테스트 + 문서 (language.md §5 신설, errors.md, README 등).
- 제외:
  - `Option` 전파 (`try`는 `Result` 전용 — Option은 `Option.okOr`로 변환).
  - match 암 블록 내부의 try (v1에서는 에러; 추후 별도 태스크로 완화 검토).
  - Rust `From` 스타일 에러 타입 자동 변환.

## 의사결정

### 결정 1: 구문은 후위 `?`가 아니라 전위 `try` 문

- **상황**: Rust는 후위 `expr?`를 쓰지만 TypeScript에서 `?`는 옵셔널
  체이닝(`a?.b`), 삼항(`c ? a : b`), 널 병합(`??`), 옵셔널 멤버(`x?: T`)에
  전부 쓰인다.
- **검토한 대안**:
  - 후위 `?`: `f()?.method()`가 옵셔널 체이닝과 문자 그대로 충돌한다.
    `f()?;`처럼 세미콜론 직전만 허용하는 축소판은 합성이 안 되고 배우기
    어렵다.
  - 전위 `try <식>` (Zig의 `try`와 동일한 의미): **표현식 위치의 `try`는
    유효한 TypeScript에 존재할 수 없다** — `try`는 예약어라 식별자가 될 수
    없고, 문(statement)으로는 `try { ... } catch` 블록뿐이다. 따라서
    `= try <식>` / 문두 `try <식>;`을 변환해도 유효한 TS를 오변환할 수 없어
    통과 계약(설계 계약 1)이 구조적으로 지켜진다.
- **선택과 근거**: 전위 `try`. 계약 안전성이 증명 가능하고(위), Rust
  사용자에게도 `try`라는 단어의 의미가 즉시 통한다.

### 결정 2: 문(statement) 수준 변환 — IIFE를 쓰지 않는다

- **상황**: 조기 리턴은 **둘러싼 함수**에서 나가야 한다. match처럼 IIFE로
  감싸면 IIFE에서만 리턴되어 의미가 틀어진다.
- **검토한 대안**: IIFE + 센티널 throw/catch (함수 경계 감지가 필요해 바이트
  스캐너로는 불가능, 런타임 비용) vs. 문 수준 인라인 방출.
- **선택과 근거**: 문 수준 인라인. `const $rl_tN = (<식>); if ($rl_tN.kind
  !== "Ok") return $rl_tN; const <바인딩> = $rl_tN.value;` 한 줄 — 함수
  컨텍스트를 그대로 쓰므로 `await`도 자연스럽고 런타임 오버헤드가 없다.
  임시 변수는 파일 단위 카운터(`$rl_t0`, `$rl_t1`, ...)로 유일성을 보장.

### 결정 3: match·템플릿 보간 내부의 try는 컴파일 에러

- **상황**: 파서는 평탄(flat)해서 함수 경계를 모른다. match 암 블록은 switch
  IIFE 안으로 컴파일되므로 그 안의 `return $rl_tN`은 함수가 아니라 **match의
  값**이 되어 Rust와 다른 의미가 된다. 스크루티니·보간은 아예 식 위치라
  문장을 넣을 수 없다.
- **검토한 대안**: ① 조용히 "match 값으로 조기 탈출" 의미 부여 — 일관성은
  있지만 Rust와 미묘하게 달라 오해를 부른다. ② sema 에러로 금지.
- **선택과 근거**: ② 금지. 파서의 재귀 Program(중첩 컨텍스트)에서 발견된
  try는 `` `try` cannot be used inside ... ``로 즉시 에러. 나중에 의미를
  정해 완화할 여지를 남긴다 (에러였던 것을 허용하는 건 하위 호환).
  모듈 최상위(함수 밖) try는 바이트 스캐너로 감지할 수 없어 문서로 안내하고
  생성물 자가 검증(top-level return은 모듈에서 파스 에러)이 잡는다.

### 결정 4: 유효한 TS의 `try` 형태를 구조적으로 배제하는 스캔 규칙

- **상황**: `try`는 멤버 이름으로는 합법이다: `obj.try(x)`, `{ try: 1 }`,
  `class A { try = 5 }`, `interface I { try?(x): void }`, `try<T>(x: T);` 등.
- **선택과 근거**: 파스 시도 자체를 다음 규칙으로 제한 — ① `.` 뒤의 `try`
  제외(기존 `match`와 동일), ② `try` 다음 유의미 문자가 `{`면 제외(try
  블록), ③ 식의 첫 문자는 식을 시작할 수 있는 문자여야 함(`? : = < , )` 등
  제외 — 인터페이스의 옵셔널/제네릭 시그니처 배제), ④ 스캔 중 최상위
  `{` / 닫는 괄호 / `,` / `=`(=>` 제외) / 짝 없는 `:`를 만나면 중단(클래스
  필드·메서드·시그니처 배제). 규칙에 걸리면 원문 통과 — 통과 계약 유지.
  이 조합이 배제하는 형태는 passthrough 테스트로 고정한다.

## 이슈 및 해결

### 이슈 1: 인터페이스의 `try<T>(x: T);` 시그니처가 식 스캔을 통과

- **증상**: 초기 스캔 규칙에서 `interface I { try<T>(x: T); }`의 멤버가
  `try` 문 후보로 파싱되어 유효한 TS를 오변환할 수 있음을 설계 리뷰에서 발견
  (반환 타입 주석이 없으면 `:` 중단 규칙에 걸리지 않음).
- **원인**: `<`가 식 시작 문자 화이트리스트에 있었음 (레거시 타입 단언
  `<T>x` 용도) — 제네릭 메서드 시그니처와 구분 불가.
- **해결**: `<`를 식 시작 화이트리스트에서 제외 (규칙 ③). 레거시 타입 단언은
  `.tsx` 미지원과 같은 맥락에서 `as`로 대체 가능. 해당 형태를 passthrough
  테스트로 고정.
