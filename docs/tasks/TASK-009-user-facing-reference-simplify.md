## 목적

"문서가 라이브러리 형태여야 하는데 내부 동작까지 담겨 너무 세세하다" 이슈 대응.
TASK-007에서 작성한 `docs/reference/`는 구현 명세 수준(바이트 스캔 규칙, 정규식
휴리스틱, 판별 규칙의 안전성 증명, 소진성 검사 알고리즘 단계, 방출 코드의 내부
설계 근거 등)까지 담고 있다. 라이브러리 사용자에게 필요한 것은 "무엇을 쓸 수
있고, 무엇이 나오고, 에러가 나면 어떻게 고치는가"이므로, 레퍼런스를 사용자
관점으로 단순화하고 내부 동작 설명은 `docs/design/` 영역에 남긴다.

## 범위

- 포함:
  - `docs/reference/language.md` — 내부 구현 상세 제거, 사용자 관찰 가능한
    동작(문법, 구분 규칙, 생성 코드, 검사, 제한사항)만 남기고 재작성
  - `docs/reference/errors.md` — Rust 내부 타입·에러 계층 설계 설명 제거,
    메시지별 원인/해결 중심으로 정리
  - `docs/reference/cli.md` — 소폭 정리 (구현 도구 언급 축소)
  - `README.md` — 내부 동작을 설명하는 "동작 원리" 절 제거
  - `CHANGELOG.md` 기록
- 제외:
  - 언어·CLI 동작 변경 (문서만 수정)
  - `docs/design/` 수정 (내부 동작 문서는 설계 문서의 역할로 유지)
  - rustdoc 수정

## 의사결정

### 결정 1: 내부 상세는 삭제하고 design 문서를 안내

- **상황**: 레퍼런스에서 걷어낸 내부 상세(스캔 규칙, 알고리즘 등)를 어디로
  옮길지.
- **검토한 대안**:
  - A. `docs/reference/internals.md`로 이동 — 내용은 보존되지만 "reference =
    사용자 문서"라는 구분이 다시 흐려진다.
  - B. 삭제하고 내부 동작이 궁금한 독자는 `docs/design/`과 소스로 안내 —
    내부 상세의 진실 소스는 어차피 구현이고, 설계 배경은 design 문서가 이미
    담당한다.
- **선택과 근거**: B. 이슈의 요지가 "사용자 문서에 내부 동작이 섞여 있다"이므로
  경계를 명확히 한다. 잃는 정보는 구현·설계 문서에서 복원 가능한 것들이다.

### 결정 2: 문법(EBNF)·생성 코드 예제는 유지

- **상황**: 어디까지가 "사용자에게 필요한 상세"인지 기준이 필요했다.
- **검토한 대안**: 문법 표기까지 제거하고 예제만 남기기 / 문법과 입출력 예제는
  유지하고 "왜 그렇게 구현됐는지"만 제거.
- **선택과 근거**: 후자. 문법과 생성 코드는 사용자가 직접 보고 다루는 표면이다
  (생성된 `.ts`는 사용자의 빌드에 들어간다). 반면 스캔 방식, 판별 규칙의 안전성
  증명, `break;`를 쓰는 이유, 소진성 검사의 후보 선택 알고리즘 같은 것은
  컴파일러 내부 사정이므로 제거 대상이다.

### 결정 3: 레퍼런스의 규범성은 유지

- **상황**: CLAUDE.md 컨벤션은 "레퍼런스는 규범 문서, 구현과 어긋나면 버그"를
  요구한다. 단순화가 이 계약을 깨는지 검토했다.
- **선택과 근거**: 유지한다. 단순화는 서술 범위를 "사용자 관찰 가능한 표면"으로
  좁히는 것이지, 남는 서술의 정확성 요구를 낮추는 것이 아니다. 남긴 문장은
  전부 기존 규범 서술에서 가져와 의미를 보존했다.
