## 의사결정

### 결정 1: 한 페이지 문서 탐색기로 만든다

- **상황**: 홈페이지는 단순해야 하지만 기능별로 가능한 것과 제한사항을 상세히 보여줘야 한다.
- **검토한 대안**: 긴 단일 문서는 탐색이 느리고, 기능별 경로 라우팅은 GitHub Pages 폴백과 배포 구성이 복잡해진다. 한 페이지의 선택형 패널은 정적 배포와 빠른 전환을 함께 만족한다.
- **선택과 근거**: 상단에는 짧은 언어 소개와 설치 명령만 두고, 아래에는 고정된 왼쪽 목록과 선택한 항목의 상세 패널을 둔다. 선택 상태는 쿼리 문자열로 보존한다.

### 결정 2: 빌드 없는 브라우저 번들로 배포한다

- **상황**: 공식 사이트의 유지 비용과 Pages 배포 단계를 최소화해야 한다.
- **검토한 대안**: 프레임워크와 빌드 도구를 추가하면 의존성과 산출 단계가 생긴다. 일반 HTML 한 파일은 상세 패널 상태와 컴포넌트 경계를 관리하기 어렵다.
- **선택과 근거**: 브라우저에서 직접 실행되는 작은 런타임과 콘텐츠 청크를 `website/dist`에 커밋한다. Pages는 이 정적 디렉터리를 그대로 배포한다.

### 결정 3: 공식 언어 사이트의 정보 계층만 참고한다

- **상황**: 시각적 장식보다 언어와 예제가 먼저 보여야 한다.
- **검토한 대안**: 제품형 랜딩 페이지는 홍보 섹션이 늘어나고, 전통 레퍼런스 한 페이지는 첫 방문자에게 무겁다.
- **선택과 근거**: Zig 홈페이지처럼 한 문장 가치와 코드 예제를 먼저 보여주고, Zig 레퍼런스처럼 목차에서 기능을 선택하게 한다. Lua처럼 전역 내비게이션은 최소화한다.
