## 목적

rlc가 "문제가 생겼을 때 그 케이스만 막는 코드"로 자라고 있는지 한 관점으로
전수 점검한다. 판단 기준은 하나다: 어떤 규칙이 한 곳에서 한 번 정의되고
모든 소비자가 그것을 읽는가, 아니면 필요할 때마다 다시 쓰였는가.

## 범위

- 포함: 소스 전체(28,521줄)의 계층 구조·중복 규칙·프로토콜 일관성 점검,
  절대 불변 원칙 #1의 실제 성립 여부를 외부 코퍼스로 측정, 성능 스케일링
  측정, 규범 문서와 실제 구조의 대조. 결과를
  [`docs/design/structural-review.md`](../design/structural-review.md)에 기록.
- 제외: **코드 수정 없음.** 발견 각각은 별도 태스크로 등록해 진행한다.
  범위를 리뷰로 한정한 이유는 아래 결정 3.

## 의사결정

### 결정 1: 불변 원칙 #1을 예시가 아니라 외부 코퍼스로 검증한다

- **상황**: "모든 유효한 TypeScript는 그대로 유효한 `.rl`"이 실제로
  성립하는지 확인해야 하는데, 저장소의 근거는 `tests/passthrough.rs`의
  손으로 고른 56개 `#[test]`뿐이다. 이 테스트 집합 자체가 "케이스별로
  짜인" 것이라 스스로를 검증하지 못한다.
- **검토한 대안**:
  - (A) 기존 테스트를 읽고 커버리지 공백을 눈으로 추정 — 값싸지만 결론이
    인상에 머문다. 실제 위반을 제시하지 못한다.
  - (B) 저장소 내 `.ts`/`.tsx` 39개로 확인 — 손쉽지만 표본이 작고 코드
    스타일이 한쪽에 치우쳐 있다.
  - (C) 컨테이너에 설치된 npm의 `node_modules` `.d.ts` 1068개를 코퍼스로
    사용 — 실제 배포되는 서드파티 TypeScript, 앰비언트 선언·오버로드·
    조건부 타입 등 손으로 떠올리기 어려운 형태가 자연히 포함된다.
- **선택과 근거**: (C). 재현 절차:

  ```sh
  find / -path '*node_modules*' -name '*.d.ts' | \
    awk '{printf "cp %s corp/f%d.rl\n", $0, NR}' | sh
  rlc -o out corp                 # 22/1068 거부
  rlc --no-verify -o out corp     # 1068/1068 바이트 동일
  ```

  이 한 번의 측정이 두 결론을 동시에 냈다. 변환기의 구문 판별 규칙은
  실제로 견고하고(불일치 0건), 자가 검사 계층은 불변 원칙을 깨고 있다
  (2.1% 오탐). (A)나 (B)로는 어느 쪽도 확정할 수 없었다.

### 결정 2: 성능 주장은 측정으로만 적는다

- **상황**: `in_function_body`와 `validate_semantic`에서 O(n²) 형태를
  읽었지만, 코드 모양만으로 "느리다"고 적으면 우선순위를 세울 수 없다.
- **검토한 대안**:
  - (A) 복잡도만 서술 — 근거가 약하고 실제 상수를 모른다.
  - (B) callgrind 프로파일만 첨부 — 핫스팟은 보이지만 스케일링은 안 보인다.
  - (C) 스케일링 벤치 + 프로파일 + 국소 패치 실험.
- **선택과 근거**: (C). 순수 TS 통과를 대조군으로 두고 `try`/`match`를
  n=1000/2000/4000으로 늘려 측정(release, 3회 최소값):

  | 파일 | 1000 | 2000 | 4000 |
  |------|------|------|------|
  | 순수 TS 통과 | 5 ms | 7 ms | 9 ms |
  | `try` n개 | 19 ms | 55 ms | 238 ms |
  | `match` n개 | 47 ms | 105 ms | 270 ms |

  통과가 선형인데 두 구문은 배가마다 2.5배씩 늘어 원인이 구문 처리에
  있음을 분리해 냈다. callgrind(`--tool=callgrind`,
  `CARGO_PROFILE_RELEASE_STRIP=none`)는 상위가 전부
  `hash_one`/`sip::Hasher::write`, 귀속은 `analysis::semantics_over`였다.
  확증을 위해 `validate_semantic`의 내부 선형 탐색만 사전 인덱스로 바꿔
  재측정해 n=4000에서 270 → 196 ms를 확인하고 즉시 되돌렸다.

### 결정 3: 리뷰에서 코드를 고치지 않는다

- **상황**: 발견 2(verify 책임 축소)는 한두 줄로 "고칠" 수 있어 보인다 —
  `tsx: true`를 켜거나 앰비언트 파싱 플래그를 주면 22건이 사라진다.
- **검토한 대안**:
  - (A) 즉시 수정 — 오늘 22건은 사라진다. 그러나 그 수정 자체가 이 리뷰가
    찾는 바로 그 패턴이다(발견된 케이스만 막기). swc를 올릴 때마다 같은
    종류가 다시 생긴다.
  - (B) 올바른 구조로 즉시 수정(verify를 생성 바이트로 한정) — 방향은
    맞지만 `mappings`/`anchors` 역매핑, 진단 문구 변경, 에디터 경로의
    `projection_accepts_diagnostics`까지 함께 걸린다. 리뷰 커밋에 섞을
    크기가 아니다.
  - (C) 리뷰는 리뷰로 끝내고 발견별 태스크를 제안한다.
- **선택과 근거**: (C). 발견 9(규범 문서가 두 리팩토링 뒤처짐)이 먼저
  고쳐지지 않으면 발견 2의 수정이 어느 계층에 들어가야 하는지조차
  현재 지도로는 판단할 수 없다. 리뷰 문서에 순서까지 포함한 우선순위표를
  남기고 착수 여부는 사용자 결정에 맡긴다.

### 결정 4: 게이트 실행 결과를 리뷰 대상에 포함한다

- **상황**: 리뷰 끝에 관례대로 검증 게이트를 돌렸더니 `cargo test`가 실패했다
  (`engine_cache::an_error_node_keeps_its_file_and_other_files_checkable`).
  내 변경은 문서 3개뿐이라 원인일 수 없었다.
- **검토한 대안**:
  - (A) 문서 변경이므로 무관하다고 보고 "게이트 통과(기존 실패 1건)"로 적음 —
    가장 빠르지만, 리뷰가 찾으려던 바로 그 종류의 문제를 눈앞에 두고
    지나친다.
  - (B) 실패를 고치고 리뷰에 포함 — 결정 3(코드 수정 없음)을 스스로 깬다.
    게다가 올바른 수정은 `defer_to_checker` 결정 지점 자체를 옮기는 것이라
    리뷰 커밋 크기를 넘는다.
  - (C) 원인까지 규명해 리뷰의 발견으로 편입하고, 수정은 후속 태스크로.
- **선택과 근거**: (C). `git stash -u` 후 `HEAD`(e11a170)에서 재현해 기존
  실패임을 먼저 확정했고(3회 반복, 결정적), 이어 같은 두 파일을 CLI로
  돌려 **엔진 경로와 CLI 경로의 답이 다르다**는 것을 분리해 냈다. 코드
  추적 결과 `engine/projection.rs`의 무조건 `defer_to_checker: true`와
  `engine/semantics.rs`의 `answers.tag_members` 의존이 만나 백엔드 부재 시
  소진성이 통째로 사라진다는 것을 확인했다. 이것은 표면적인 테스트 실패가
  아니라 절대 불변 원칙 #2 위반이며, 리뷰의 최우선 발견이 되어야 했다
  (발견 1). (A)를 택했다면 리뷰의 결론 자체가 틀렸을 것이다.

## 이슈 및 해결

### 이슈 1: release 프로파일이 심볼을 제거해 프로파일에 함수명이 없었다

- **증상**: `callgrind_annotate` 결과가 전부
  `???:0x000000000025ee00 [rlc]` 형태로 나와 귀속이 불가능했다.
- **원인**: `Cargo.toml`의 `[profile.release]`에 `strip = "symbols"`.
- **해결**: `CARGO_PROFILE_RELEASE_STRIP=none CARGO_PROFILE_RELEASE_DEBUG=1`로
  재빌드해 프로파일을 얻고, 벤치 수치는 원래 설정으로 다시 빌드해서
  측정했다(스트립 여부가 코드 생성에 영향을 주지 않도록 분리).

### 이슈 2: 코퍼스 바이트 비교가 전건 불일치로 나왔다

- **증상**: 첫 비교에서 39/39, 이어 1068/1068이 모두 "다름"으로 나와
  통과 계약이 완전히 깨진 것처럼 보였다.
- **원인**: `rlc -o`가 출력 선두에
  `// @generated from <file> by rlc — do not edit directly.` 배너 한 줄을
  붙인다. `diff`로 실제 차이를 열어 보고 확인했다.
- **해결**: 비교 전 `tail -n +2`로 배너를 제거. 이후 변환 불일치 0건.
  리뷰 문서의 재현 절차에도 이 단계를 반영했다.

### 이슈 3: `match` 벤치가 `in_function_body`로 설명되지 않았다

- **증상**: `try`의 초선형은 `in_function_body`로 설명됐지만, `match`는
  그 함수를 부르지 않는데도 같은 곡선을 그렸다. 원인 미상이면 발견 5가
  과대평가된 것일 수 있었다.
- **원인**: callgrind 귀속이 `analysis::semantics_over`를 가리켰고, 그
  안의 `validate_semantic`이 match마다 `hir.sites`를 선형 탐색하며
  HashMap 기반 `node_span`을 호출하고 있었다. `assert!`라 릴리스에서도
  실행된다.
- **해결**: 별개 원인으로 확정해 발견 4로 분리하고, 국소 패치 실험으로
  기여분(4000에서 270 → 196 ms)을 측정한 뒤 되돌렸다. 두 발견 모두 근거를
  갖게 됐다.

### 이슈 4: 저장소 `.tsx` 6건의 거부가 범위 밖일 수 있었다

- **증상**: `.tsx` 파일이 verify에서 거부되지만, rl은 `.rl → .ts`이므로
  JSX가 애초에 계약 밖이라는 반론이 가능했다.
- **원인/판단**: `.d.ts` 코퍼스에서 나온 앰비언트 선언과 `arguments`
  거부는 JSX와 무관한 순수 `.ts`다. 즉 `.tsx`는 같은 근본 원인(자가 검사가
  통과 영역까지 남의 파서로 검사)의 한 사례일 뿐이고, 근본 원인은 `.tsx`
  없이도 성립한다.
- **해결**: 발견 2의 주장을 `.ts` 증거만으로 세우고 `.tsx`는 부수 사례로
  각주 처리했다.

### 이슈 5: `cargo test`가 기존에 이미 실패하고 있었다

- **증상**: `engine_cache::an_error_node_keeps_its_file_and_other_files_checkable`가
  진단 2건을 기대하는데 1건만 받는다
  (`assertion left == right; left: 1, right: 2`). 빠진 것은 소진되지 않은
  `match`의 진단이다.
- **원인**: `git stash -u` 후 `HEAD`(e11a170)에서 3회 재현해 내 변경과
  무관한 결정적 실패임을 확인했다. 추적하니
  `engine/projection.rs`가 투영 시점에 무조건 `defer_to_checker: true`로
  열어 rlc 자신의 소진성 보고를 끄고(`sema.rs`의
  `if !defer_to_checker { report_coverage(...) }`),
  `engine/semantics.rs`는 `answers.tag_members`로만 소진성을 재계산한다.
  TypeScript 7 백엔드가 없으면 `answers`가 비어 모든 파일이 `continue`되고
  검사가 사라진다. CI는 `typescript@7`을 설치하므로 이 구성을 한 번도
  실행하지 않는다.
- **해결**: 이 태스크에서는 고치지 않았다(결정 3·4). 발견 1로 문서화하고
  우선순위 2위로 올렸다. 남은 부채: 백엔드 폴백 규칙 도입과, 백엔드 없는
  구성을 도는 CI 잡. 그때까지 이 저장소의 `cargo test`는 TypeScript 7
  툴체인이 없는 환경에서 빨간불이다.

경계)은 이미 구조로 해결돼 있고, 변환 자체도 실측 1068개 파일에서 바이트
동일하다. "케이스별로 짜였을까"라는 물음의 답은 대체로 아니오다.

남은 문제는 케이스별 코드가 아니라 **층 사이 약속의 한쪽만 적힌 자리**다:
(a) 엔진이 소진성을 체커에 위임해 놓고 체커가 없을 때의 폴백이 없어
불변 원칙 #2가 깨져 있고(발견 1, 지금 `cargo test` 빨간불),
(b) 자가 검사가 통과 영역까지 남의 파서로 검사해 불변 원칙 #1이 깨져 있고
(발견 2, 실측 2.1% 오탐), (c) 두 계약을 지켜야 할 게이트가 손으로 고른
56 케이스와 백엔드 있는 구성 하나뿐이며(발견 3), (d) 규범 문서가 두
리팩토링 뒤처져 잘못된 계층을 가리킨다(발견 9).

후속 태스크는 리뷰 문서의 우선순위표를 따르며, 착수 전 등록한다.
