## 의사결정

### 결정 1: 라이브러리 `pipe()` 함수가 아니라 전용 연산자 `|>`

- **상황**: "각 체이닝 단계에서 정확한 타입 추론"을 달성하는 방식 선택.
- **검토한 대안**: (A) std에 Ramda식 `pipe(...)` 함수 추가 — 구현 비용 0에
  가깝지만 TS의 고정 arity 오버로드 한계와 제네릭 함수 합성 시 `unknown`
  붕괴(고차 제네릭 추론 불가) 때문에 요구를 원천적으로 충족 불가. (B) 전용
  연산자를 단계별 직접 함수 적용으로 디슈가 — 생성물이 평범한 호출 나열이라
  tsc가 각 단계를 독립·완전 추론.
- **선택과 근거**: (B). 요구사항이 (A)로는 달성 불가능하고, (B)는 "rlc는
  구조만, 타입은 tsc" 에러 계층 계약과도 정확히 일치한다.

### 결정 2: F# 스타일(`x |> f` → `f(x)`) 채택, Hack 스타일(topic `%`) 기각

- **상황**: TC39에서 경쟁한 두 파이프 의미론 중 선택.
- **검토한 대안**: Hack 스타일은 다인자에 편하지만 topic 토큰을 step 식
  **내부**에서 찾아야 해 식 수준 파싱이 필요하고(`%`가 topic인지 나머지
  연산인지는 피연산자 위치를 알아야 구분), rl의 오류 없는 바이트 단위 구조
  파서 아키텍처와 충돌. F# 스타일은 최상위 `|>` 분리만으로 파싱이 완결된다.
- **선택과 근거**: F# 스타일. 파서 아키텍처 정합 + "Ramda처럼"(data-last
  커링) 요구와 정확히 일치. 다인자는 커링 호출 또는 괄호 화살표 step으로 해결.

### 결정 3: 방출은 중첩 호출이 아니라 단계별 const IIFE

- **상황**: `g(f(x))` 중첩 호출 방출이 더 짧지만, JS는 callee를 인자보다 먼저
  평가하므로 step 식이 오른쪽부터 평가된다.
- **검토한 대안**: (A) 중첩 호출 — 짧음, 평가 순서 어긋남. (B) 화살표 IIFE +
  `const $rl_pN` — 좌→우 평가 보장, 단계별 타입이 생성물에 물질화, 디버깅
  용이, match의 switch IIFE 선례와 일관.
- **선택과 근거**: (B). 평가 순서는 의미론이고("Rust처럼"), 추론 품질은 동일.

### 결정 4: 스트레이 `|>`는 통과가 아니라 sema 에러

- **상황**: 구조 파싱에 실패한 `|>`를 기존 구문처럼 원문 통과시키면 생성물이
  유효하지 않은 TS가 되어 출력 자가 검사에서 위치 정보 없이 실패한다.
- **검토한 대안**: (A) 통과 후 verify 실패 — 에러 계층 계약(rl 수준 에러는
  rlc가 위치와 함께 보고) 위반. (B) sema가 verbatim 구간의 `|>`를 검출해
  `파일:행:열` 에러로 보고.
- **선택과 근거**: (B). `|>`는 유효 TS에 존재할 수 없는 토큰 열이므로 에러로
  보고해도 통과 계약("모든 유효한 TS는 유효한 rl")은 깨지지 않는다.

### 결정 5 (개정): std data-last 커링 변형(`*P`)을 연산자와 동시 도입

- **상황**: 현재 std 콤비네이터는 data-first(`Option.map(o, f)`)라 파이프에
  바로 안 맞는다. 초안에서는 후속 분리였으나, 사용자 피드백(화살표 래핑의
  불편)으로 승격을 결정.
- **검토한 대안**: 네이밍 — (A) 같은 객체에 `P` 접미사 변형 추가, (B) 별도
  네임스페이스(`OptionP.map`): import 이중화, (C) 기존 API를 data-last로
  교체: 기존 사용자 파손.
- **선택과 근거**: (A). 호환성 무손상 + 추가 import 불필요. F#이 화살표 없는
  파이프를 쓸 수 있는 이유가 "커링 + data-last 표준 라이브러리"라는 사실에
  대응하는 rl 측 답이다.

### 결정 6: 방출은 직접 적용이 아니라 `$rl_ap` 헬퍼 중첩 (tsc로 검증)

- **상황**: 커링 콤비네이터 `Option.mapP(x => x + 1)`의 화살표 인자가 주석
  없이 추론되는지가 제안 전체의 성패를 가른다.
- **검토한 대안**: (A) 직접 적용 중첩 `(step)(prev)`, (B) IIFE + 단계별
  const + 직접 적용(초안 채택안), (C) 파일당 1회 방출하는
  `const $rl_ap = <A, B>(v: A, f: (v: A) => B): B => f(v)` 헬퍼 중첩.
- **선택과 근거**: (C). `tsc --strict --noEmit` 실측으로 (A)·(B)는 커링
  스텝에서 `error TS18046: 'x' is of type 'unknown'` — callee 위치는 문맥
  타입을 받지 못해 역방향 추론이 안 된다. (C)는 step이 인자 위치에 놓여
  반환 타입 문맥 추론(fp-ts `pipe` 메커니즘)이 작동해 통과했다. 부수적으로
  `$rl_ap` 중첩은 인자 평가 규칙 덕에 좌→우 평가가 되고 IIFE가 사라져
  await도 async 감지 없이 자연 동작한다 — 초안의 IIFE 채택 사유(평가 순서)가
  더 나은 방식으로 해소되어 초안 결정 3을 대체한다.

### 결정 7: 메서드 스텝 `|> .method()` 채택

- **상황**: 네이티브 메서드(문자열/배열 등)는 커링 std로 덮을 수 없어 화살표
  래핑이 남는다. 사용자가 메서드 체이닝 지원을 요청.
- **검토한 대안**: (A) step이 `.` + 식별자로 시작하면 파이프 값에 대한
  포스트픽스 체인으로 해석 — 첫 유의 바이트만 보면 되므로 바이트 단위 구조
  파싱과 호환. (B) Hack 스타일 topic 재검토 — 결정 2의 기각 사유(식 수준
  파싱 필요)가 그대로 유효.
- **선택과 근거**: (A). `x |> .trim()` → `(x).trim()` — 방출이 평범한 멤버
  접근이라 추론 자명, Rust 체이닝 감각 직결.

### 결정 8: Option/Result에 진짜 메서드(클래스화)는 하지 않음

- **상황**: Rust처럼 `opt.map(f)` 실제 메서드를 원하는 요구의 다른 해석.
- **검토한 대안**: std 값을 클래스 인스턴스로 만들면 메서드는 얻지만, "std
  선언은 rl enum 컴파일 결과와 정확히 같은 형태"라는 계약(stdlib.rs 바이트
  일치 테스트)과 JSON 직렬화·구조적 동등성이 깨진다.
- **선택과 근거**: 클래스화 기각. 메서드 스텝 + 커링 std 조합이 순수 데이터
  위에서 같은 체감을 제공한다 (제안 문서 §7.1).

## 이슈 및 해결

### 이슈 0: 초안의 방출 형태로는 커링 콤비네이터 추론이 깨짐

- **증상**: 초안 방출(IIFE + `(step)($rl_pN)` 직접 적용)을 tsc로 시뮬레이션
  하자 `Option.mapP(x => x + 1)` 스텝에서
  `error TS18046: 'x' is of type 'unknown'`.
- **원인**: TS는 역방향(Hindley-Milner식) 유추를 하지 않고, callee 위치의
  식은 문맥 타입을 받지 못한다. 커링 함수를 데이터 없이 먼저 호출하는 시점에
  `T`의 추론 소스가 없어 `unknown`으로 붕괴 — Ramda 단독 사용 시의 고질
  문제와 동일 원인.
- **해결**: step을 타입이 달린 2인자 헬퍼 `$rl_ap(값, 함수)`의 인자 위치로
  옮겨 반환 타입 문맥 추론(fp-ts `pipe` 메커니즘)을 작동시킴. tsc 실측 통과
  확인 후 방출 설계를 교체(결정 6). 채팅 제안 단계에서 실측으로 걸러냈고,
  구현 태스크의 integration.rs에 동일 케이스를 옮겨 회귀를 방지한다.

### 이슈 1: head가 이미 분리된 세그먼트(템플릿 등)를 포함할 수 있음

- **증상**: 스캔 루프는 템플릿 리터럴을 만나면 즉시 `Segment::Template`으로
  분리하므로, `` `s${x}` |> f ``에서 `|>` 발견 시점에 head의 일부가 이미
  세그먼트로 방출되어 있다.
- **원인**: 파이프는 rl 최초의 **중위** 구문이라 head를 뒤늦게 클레임해야 함.
- **해결**: 세그먼트가 스팬 기반이므로 head 시작 오프셋 이후의 세그먼트를
  되감아 head의 하위 Program으로 흡수하는 방식을 제안 문서 §5에 명시. 실제
  구현 시 검증 필요(구현 태스크로 이관).
