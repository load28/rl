케이스 태그와 페이로드 필드 이름은 방출 TypeScript에 존재하지 않으므로
(태그는 문자열 리터럴, 필드는 구조 분해 키) 체커에게 "여기 뭐가 올 수 있냐"를

## 의사결정

### 결정 1: 자리 판정을 파서가 아니라 토큰 스트림으로 한다

- **상황**: 완성은 **구문이 아직 완성되지 않은** 순간에 요청된다
  (`match (s) { Circle(r) => r, Po|` — 마지막 암에 본문이 없다). 파서는 계약상
  전부-아니면-전무다(완전히 파싱될 때만 청구). 파서에 기대면 정작 필요한 순간에
  아무것도 모른다.
- **검토한 대안**:
  - (a) 프로브로 텍스트를 기워 파싱시키기(`_ => 0`을 끼워 넣는 식) — 어떤
    미완성 상태를 어떻게 기울지가 경우마다 다르고, 기운 텍스트가 또 실패하면
    답이 없다.
  - (b) 토큰 스트림에서 자리만 읽기 — 렉서는 **어떤 텍스트에 대해서도** 정의된다.
    선언(enum)만 파스에서 가져오는데, 편집 중인 match 옆의 선언은 대개 완성돼
    있다.
- **선택과 근거**: (b). "완성이 필요한 순간에 답한다"가 이 기능의 존재 이유이고,
  (a)는 그 순간에 가장 약하다. 정규식이 아니라 **프로젝트의 렉서**를 쓰므로
  문자열·주석·템플릿 안이 자동으로 배제된다(에디터 구현이 `maskNonCode`로 따로
  하던 일).

### 결정 2: 이미 쓴 케이스를 빼지 않고 표시만 한다

- **상황**: 에디터의 기존 arm 완성은 이미 커버된 태그를 목록에서 **뺀다**.
- **검토한 대안**: 빼기 / `covered` 플래그로 표시.
- **선택과 근거**: 표시. 가드 암(`A if c => ...`)을 여러 개 쓰는 것은 정상이고,
  뺐다면 두 번째 가드 암을 쓸 때 완성이 침묵한다. 정렬·흐리기는 소비자가
  정할 일이라 사실만 넘긴다.

### 결정 3: `if let`은 모든 enum의 케이스를 답한다

- **상황**: `if let So|`에는 어느 enum인지 말해 주는 것이 아무것도 없다(match는
  다른 암의 태그가 말해 준다).
- **검토한 대안**: 침묵 / 보이는 모든 케이스.
- **선택과 근거**: 후자. 편집기가 접두사로 거르므로 `So`까지 치면 `Some`만
  남는다. `if let`은 rl 전용 구문이라 다른 해석이 없어 오답 위험도 없다.

## 이슈 및 해결

### 이슈 1: 타이핑 중인 접두사가 "이미 쓴 암"으로 세어짐

- **증상**: `match (s) { Circle(r) => r, Po| }`에서 완성이 빈 목록을 답했다.
- **원인**: 암 태그 수집이 본문의 최상위 식별자를 전부 모으는데, 커서 아래의
  `Po`도 그중 하나로 세었다. 그러면 태그 집합이 `{Circle, Po}`가 되고, 그것을
  모두 가진 enum이 없으니 subject 해석이 실패한다.
- **해결**: 커서가 걸친 식별자 토큰의 인덱스를 `prefix`로 계산해 수집에서
  제외했다. 커서가 식별자의 **앞**에 있든 **끝**에 있든 같은 토큰을 가리키도록
  두 경우를 모두 본다.
