## 목적

`--native-check`는 실행마다 tsgo API 서버를 새로 띄우고 프로젝트를 새로
연다. 감시 모드와 에디터에서는 하나의 의미 상태를 유지하고 바뀐 파일만
갱신해야 한다.

## 범위

- 포함: 호스트 프로세스를 살려 두는 형태(요청 스트림), `updateSnapshot`의
  `fileChanges`로 증분 갱신, `-w` 감시 모드 연결, 측정.
- 제외: Rust 네이티브 IPC 클라이언트로의 교체 (TASK-073 결정 3 — 프로토콜이
  안정화되면 별도로 판단).

## 조사 메모 (TASK-073)

- `updateSnapshot({ fileChanges: { changed, created, deleted } })`가 있다.
- 배치 질의는 이미 공식 API에 있다 (배열 오버로드).
- 현재 구조는 한 번의 왕복으로 프로젝트 전체를 묻는다 — 증분화의 출발점은
  호스트를 죽이지 않는 것이다.

## 의사결정

### 결정 1: 호스트를 세션으로 — 줄 단위 JSON 요청/응답

- **상황**: 호스트는 요청마다 새로 뜨고, 프로젝트를 새로 열고, 죽었다.
  실측으로 작은 프로젝트에서도 실행당 ~250 ms였고 그 대부분이 기동과
  프로젝트 열기였다.
- **검토한 대안**: (A) 요청마다 프로세스 — 지금 구조, 단순하지만 감시·에디터
  에서 감당이 안 된다. (B) 상주 호스트 + 줄 단위 JSON — stdin이 열려 있는
  동안 살아 있고, 프로젝트는 처음 한 번만 연다.
- **선택과 근거**: (B). API 클라이언트가 **동기** RPC(파이프에 `readSync`)라
  호스트 쪽 루프도 동기로 자연스럽게 쓰인다. 실측: 첫 패스 183 ms →
  이후 패스 8~12 ms.

### 결정 2: 스냅샷은 `fileChanges`로만 갱신한다

호스트가 서빙 중인 모듈 맵을 제자리에서 갱신하고, 무엇이
`changed`/`created`/`deleted`인지 계산해 `updateSnapshot({fileChanges})`에
넘긴다. 열기(`openProjects`/`openFiles`)는 첫 요청에서만 한다.

### 결정 3: 세션은 프로젝트 하나에 묶인다

`ask`가 다른 tsconfig/루트로 오면 세션을 버리고 새로 연다 — 한 세션이 두
프로젝트를 섞지 않는다.
