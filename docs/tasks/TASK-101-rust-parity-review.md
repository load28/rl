# TASK-101: rl 구문의 Rust 수준 분석 격차 검토와 개선 계획

- **상태**: 완료
- **시작일**: 2026-08-20
- **완료일**: 2026-08-20
- **커밋**: `c600a23`, `03e148c`, `a2e40b0`

## 목적

TASK-096(typed match analysis)·TASK-097(coverage 단일 원천)이 `match`에 대해
세운 기준 — 타입이 붙은 공통 분석, 체커 우선·분석 폴백, 한 규칙에 한 구현 —
을 잣대로, rl이 러스트에서 가져온 나머지 구문(`enum`·`try`·let-else·`if let`·
`|>`/`flow`·`result`·`val`)이 같은 수준으로 분석·컴파일되고 있는지, 그리고 그
분석이 LSP(타입 추론·자동완성·이동·이름 바꾸기)로 이어지는지 검토한다.

## 범위

- 포함: 구문별 실측(방출 결과·emit-map·tsc 진단)과 엔진 코드 경로 판독, 격차
  목록화, 원인 분석, 개선 계획 제안. 결과물은 설계 문서
  [`docs/design/rust-parity-analysis.md`](../design/rust-parity-analysis.md).
- 제외: 구현. 제안된 P1~P5는 승인 후 각각 별도 태스크로 등록한다. 이 태스크는
  코드를 바꾸지 않는다(문서만).

## 의사결정

### 결정 1: 결과물을 규범이 아닌 설계/검토 문서로 낸다

- **상황**: 검토 결과를 어디에 남길지. 레퍼런스(`docs/reference/`)는 규범이라
  구현되지 않은 제안을 담을 수 없다.
- **검토한 대안**:
  - (a) `docs/design/`에 검토·제안 문서 — `type-inference-gaps.md`,
    `ts7-semantic-unification.md`(TASK-082)의 선례가 있다. 채택 항목만 나중에
    레퍼런스로 옮긴다.
  - (b) 태스크 문서에만 기록 — 검토 자체가 길고 다른 태스크에서 참조될 텍스트라
    태스크 문서 안에 묻히면 찾기 어렵다.
  - (c) 곧바로 레퍼런스 갱신 — 구현되지 않은 것을 규범으로 적게 되므로 기각.
- **선택과 근거**: (a). TASK-082가 만든 선례와 정확히 같은 형태의 작업이고,
  문서 첫 줄에 "제안이며 규범이 아니다"를 명시해 혼동을 막는다.

### 결정 2: 후속 제안(P1~P5)을 지금 INDEX에 등록하지 않는다

- **상황**: 제안이 5건이고 각각 태스크 크기다. 지금 전부 `대기`로 등록할지.
- **검토한 대안**:
  - (a) 지금 5건 등록 — 승인 전 범위·순서가 바뀔 수 있어 문서 5개가 곧 낡는다.
  - (b) 검토 문서 안의 로드맵으로만 두고, 착수 시 등록 — TASK-082 → TASK-083~085가
    실제로 밟은 경로다.
- **선택과 근거**: (b). 우선순위(§7)까지 문서에 있으므로 착수 시 그대로 옮기면
  된다. 이미 등록된 TASK-100은 P4의 첫 조각이라는 관계를 문서에 명시했다.

### 결정 3: usefulness 알고리즘 교체를 잔여 항목에서 독립 제안으로 승격

- **상황**: §9를 쓰면서 P5(잔여 정리)에 묶여 있던 "중첩 패턴 내부 소진성 v2"가
  사실 알고리즘 교체 문제임이 드러났다.
- **검토한 대안**:
  - (a) 현행 곱집합 odometer에 중첩 케이스를 특별 처리로 덧붙인다 — 중첩 깊이·
    or-패턴·와일드카드 조합마다 특별 케이스가 늘고, 증거(witness) 생성과 도달
    불가 검사는 여전히 별도 구현이 된다.
  - (b) Maranget usefulness로 교체한다 — rustc가 소진성·도달 불가·증거를 한
    알고리즘으로 답하는 방식이고, rl의 패턴 문법이 rustc의 부분집합이라 그대로
    성립한다. 교체 비용이 크고 기존 `Coverage` 소비자(sema)의 회귀 위험이 있다.
- **선택과 근거**: (b)를 독립 제안으로 승격하고 순서를 P3(에디터 이관)보다
  **앞으로** 옮겼다. 에디터가 소비할 분석이 최종 형태여야 같은 표면을 두 번
  만들지 않는다. 회귀 위험은 기존 소진성 테스트가 그대로 게이트가 된다.

### 결정 4: 계약 예외보다 "덜 쓰고 있던 기구"를 먼저 쓴다

- **상황**: 타입 소유권 축(§9.3)을 개선하려면 계약 예외가 필요한가라는 질문.
  예외를 여는 설계를 바로 쓸 수도 있었다.
- **검토한 대안**:
  - (a) 검사 전용 프로젝션(프로브 심기)을 곧바로 규범화 — 강력하지만 검사한
    것과 빌드한 것이 갈리는 부채를 즉시 짊어진다.
  - (b) 계약이 이미 허용하는 기구를 먼저 소진 — 진단 앵커(방출 불변),
    seam 확장(`val`이 이미 하는 "묻되 소유하지 않기"), 진단 번역(rlc가 자기
    글루의 진단을 자기 문안으로). 셋 다 계약 문구를 건드리지 않는다.
  - (c) 산출물에 타입 트릭 — 에러 계층이 붕괴한다.
- **선택과 근거**: (b). 실제로 격차 목록을 하나씩 대보면 GAP-1·GAP-4·TASK-100·
  도달 불가 arm·폴백 정확도·witness 문안이 전부 (b)로 닫히고, **지금 알려진
  격차 중 (a)를 반드시 요구하는 것이 하나도 없다.** (a)는 필요가 관측된 뒤에
  §10.6의 규칙 여섯과 함께 여는 것으로 문서화하고, (c)는 기각했다. 확인
  방법: §10.3의 표가 격차↔질문 대응을 1:1로 적고 있어 반증 가능하다.

### 결정 5: 격차 주장은 전부 실행으로 확인한 것만 적는다

- **상황**: "LSP가 못 한다"류의 주장은 코드 읽기만으로는 틀리기 쉽다.
- **검토한 대안**: 코드 판독만 / 실행 확인 병행.
- **선택과 근거**: 병행. 방출과 매핑은 `rlc --print`·`rlc --emit-map`으로,
  새어 나오는 진단은 tsc 5.9로 직접 확인했고(§4의 에러 코드는 전부 실행
  결과다), 실행할 수 없는 부분(tsgo 미설치 환경의 엔진 응답)은 코드 경로
  (`to_service`/`map_target`/`rename`의 `None` 처리)를 인용해 판정 근거를
  남겼다.

## 이슈 및 해결

### 이슈 1: 이 환경에 tsgo가 없어 엔진 응답을 e2e로 확인할 수 없음

- **증상**: `scripts/setup`이 받아오는 `@typescript/native-preview`가 없어
  `rlc --check-types`/`--server` 경로를 실행할 수 없다.
- **원인**: 컨테이너에 툴체인이 설치되어 있지 않다.
- **해결**: 두 가지로 우회했다. (1) 타입 진단은 npm으로 tsc 5.9를 받아 방출된
  `.ts`를 직접 검사해 확인했고(위치·코드 실측), (2) 엔진의 답 처리는
  `to_service`/`from_service_span`/`map_target`/`rename`의 `None` 경로를 읽어
  판정했다 — 세 함수 모두 매핑이 없으면 질문·답·편집을 버리므로, 매핑 0개인
  구간에서의 결과는 코드로 결정된다. 남은 부채: 제안 P3 구현 시 vscode
  `engine.test.ts` 계층의 e2e 확인이 필요하다(TASK-096이 남긴 부채와 같은 자리).
