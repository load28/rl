## 목적

rl을 "tsc처럼 단독으로도 쓰고 번들러에도 붙이는" 형태로 맞추는 과정에서
빠져 있던 `tsc -w` 대응을 채운다. 한 번 컴파일하고 끝내는 대신 입력을 계속
지켜보며 바뀐 것만 다시 컴파일한다.

## 범위

- 포함: `-w, --watch` 플래그, 감시 루프, 변경 파일의 importer 재컴파일,
  `cli.md` 갱신.
- 제외: 파일 시스템 이벤트 API. 아래 결정 1 참조.
- 제외: `--symbols`·`--sidecar`와의 조합. 컴파일하지 않는 모드다.

## 의사결정

### 결정 1: 이벤트 대신 폴링으로 감시한다

- **상황**: 변경 감지 방법을 정해야 했다.
- **검토한 대안**:
  - `notify` 크레이트: OS 이벤트 API를 쓰므로 지연이 짧다. 대신 의존성이
    (전이 의존성 포함) 크게 늘고, 플랫폼별 동작 차이를 떠안는다. 현재
    `Cargo.toml`의 런타임 의존성은 swc 셋뿐이다.
  - 300ms 폴링: 표준 라이브러리만 쓴다. 파일 수가 많으면 `stat` 비용이
    들지만, 이 규모의 프로젝트에서는 무시할 만하다. 네트워크 파일
    시스템에서도 동작한다.
- **선택과 근거**: 폴링. 의존성 없이 필요한 동작을 전부 얻는다. 이벤트가
  필요할 만큼 커지면 그때 바꾸면 되고, 인터페이스(`-w`)는 그대로다.

### 결정 2: 바뀐 파일의 importer도 함께 다시 컴파일한다

- **상황**: 변경된 파일만 다시 컴파일하면 충분한지 검토했다.
- **선택과 근거**: 충분하지 않다. TASK-022 이후 소진성 검사는 **다른 파일의
  enum 선언까지** 본다. `a.rl`의 enum에 케이스가 늘면 그것을 `match`하는
  `b.rl`이 컴파일 에러가 되어야 하는데, `b.rl` 자체는 바뀌지 않았으므로
  변경 목록에 없다. 그래서 `rl_imports`로 각 입력의 직접 import를 풀어
  변경된 파일을 가리키는 것들을 함께 대상에 넣는다(`with_dependents`).
  실측으로 확인했다 (아래 작업 내역).

### 결정 3: 입력을 매 회차 다시 수집한다

- **상황**: 감시 중에 새 `.rl` 파일이 생기면 어떻게 되는지.
- **선택과 근거**: 회차마다 `build_jobs`를 다시 부른다. 디렉터리 입력이면
  새 파일이 그대로 잡힌다. 입력 경로가 잠깐 사라져도(편집 중 rename 등)
  세션을 끝내지 않고 다음 회차를 기다린다.
