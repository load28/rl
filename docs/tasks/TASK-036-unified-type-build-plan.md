## 목적

rl은 단독(tsc-only) 파이프라인과 번들러 플러그인(vite-plugin-rl) 양쪽에서 쓸
수 있지만, 두 모드가 **타입과 빌드를 만들어내는 방식이 서로 다르다**. 어느
모드에서 쓰든 같은 방식이 되도록 통일하는 개선의 전체 계획을 세운다.
(이 태스크는 계획 수립까지 — 구현은 아래 단계별 후속 태스크로 진행한다.)

## 범위

- 포함: 현황(모드 간 차이) 분석, 통일 모델 설계, 구현 단계 정의.
- 제외: 구현 자체 (각 단계를 시작할 때 TASK-037부터 등록한다).

## 현황 — 무엇이 다른가

산출물별 생산 경로 (2026-08-17, TASK-035 시점):

| 산출물 | 단독 (tsc) | 번들러 (vite-plugin-rl) |
|--------|-----------|------------------------|
| 런타임 JS | `rlc src/`가 `.ts` 트리 방출(지정자 `js`로 재작성, std는 `rl.ts`로 실체화) → tsc가 JS 방출 | 플러그인이 모듈마다 `rlc -p --rewrite-imports off`, std는 가상 모듈 → 번들러가 JS 방출 |
| 타입 (.d.ts) | tsc가 방출 트리에서 부산물로 생성 | 수동 3단계 체인: `rlc -o .rl-build` → `tsc -p tsconfig.types.json` → `rlc --sidecar … -o .rl-types`, 소비 tsconfig에 `rootDirs` |
| 에디터 경험 | 손으로 쓴 `.ts`가 방출물(`./x.js`)을 import — 정의 이동이 생성된 `.ts`로 간다 | 사이드카 — `./x.rl` import 유지, 정의 이동이 원본으로 간다 |

구체적 차이는 세 가지다.

1. **소스를 쓰는 방식부터 다르다.** 플러그인 모드에서는 손으로 쓴 `.ts`도
   `"./x.rl"`을 import하지만, 단독 모드에서는 tsc가 방출 JS의 `.rl` 지정자를
   재작성해 주지 않으므로(TS의 `rewriteRelativeImportExtensions`는 TS 확장자만
   다룬다) 방출물인 `"./x.js"`를 import해야 런타임이 성립한다. 같은
   프로젝트를 모드 간에 옮기려면 소스를 고쳐야 한다.
2. **타입 생산 경로가 다르다.** 단독은 tsc의 부산물, 플러그인은
   `tsconfig.types.json`·캐시 트리·사이드카·`rootDirs`를 사용자가 손으로 엮은
   체인이다 ([TASK-033](./TASK-033-vite-plugin.md) 결정 4, 후속 과제로 남음).
3. **오케스트레이션 주체가 셋으로 갈라져 있다.** 사용자 스크립트(단독),
   플러그인(런타임만), VSCode 확장(타입만 — tsc 선언 방출 중간 단계를
   `editors/vscode/server/src/sidecar.ts`가 자체 재구현).

## 통일 모델

한 문장 계약:

> **소스는 모드와 무관하게 동일하다** — `.rl`이든 손으로 쓴 `.ts`든 서로를
> `"./x.rl"`·`"@rl/std"`로 import한다. **타입은 언제나 rlc의 사이드카
> 파이프라인이, 런타임은 언제나 rlc의 동일한 컴파일 출력이 만든다.** 모드의
> 차이는 단 하나 — ".rl 지정자를 런타임에 누가 해석하는가"(AOT 재작성 vs
> 번들러 resolveId) — 로 줄인다.

|  | 단독 (tsc) | 번들러 (vite) |
|--|-----------|---------------|
| 소스 | `"./x.rl"`, `"@rl/std"` | **같음** |
| 타입검사·에디터 | `rlc types` → `.rl-types/` 사이드카, `tsc --noEmit` | **같음** |
| 런타임 | `rlc build`가 완결된 TS 트리 방출(지정자 재작성) → tsc | 플러그인이 같은 `compile()`을 모듈 단위로(재작성 off) → 번들러 |

이 모델이 성립하는 근거: 통과 계약의 유일한 예외가 상대 경로 `.rl` 지정자
재작성([TASK-020](./TASK-020-import-specifier-rewrite.md), `language.md` §7)
이므로, **손으로 쓴 `.ts`를 rlc에 통과시키면 지정자만 바뀌고 나머지는 바이트
동일**하게 나온다. 즉 rlc가 `.ts`까지 방출 트리에 포함시키면 단독 모드에서도
소스가 `"./x.rl"`을 import할 수 있고, 새 예외를 만들 필요가 없다.

## 단계별 계획

각 단계는 시작 시점에 개별 태스크로 등록한다 (TASK-037부터 순서대로).
모든 단계는 언어 표면 변경 시 `docs/reference/` 갱신 규칙을 따른다.

### 1단계 — `rlc build`: 소스 트리 전체를 완결된 TS 트리로

디렉터리 수집이 `.rl`만 잡는 현재 규칙에 더해, build 모드에서는 손으로 쓴
`.ts`도 수집해 통과+지정자 재작성으로 **같은 출력 트리**에 방출한다. std
실체화(TASK-035)와 `-w`(TASK-034)는 그대로 재사용. 기본 `rlc <dir>` 동작은
바꾸지 않는다 (호환성).

- 검증: 방출 트리 **단독으로** tsc 컴파일·node 실행이 성립함을
  `integration.rs`에 추가.

### 2단계 — `rlc types`: 타입 파이프라인 내재화

지금 사용자·확장에 흩어져 있는 "컴파일 → 선언 방출 → 사이드카" 체인을 rlc 한
명령으로 만든다. `rlc types [-o .rl-types] <inputs>`가:

1. 1단계 build를 캐시 트리(`.rl-build/`)로 실행하고,
2. tsc를 `--emitDeclarationOnly`로 스폰하고 (tsconfig는 rlc가 합성 —
   `rootDir`를 캐시 트리로 고정해 TASK-033 이슈 2의 경로 중첩 재발을 방지;
   `--tsconfig`로 사용자 설정 extends, `--tsc`로 바이너리 지정, 기본 탐색은
   `node_modules/.bin/tsc` → PATH),
3. `--sidecar` 단계로 `.rl-types/`를 산출한다 (`@rl/std` 선언 `rl.d.ts` 포함).

`-w`와 조합을 지원한다 (변경 파일 + importer만 재방출 — watch 그래프 재사용).
소비 tsconfig에 넣을 `rootDirs`/`paths` 스니펫을 안내로 출력한다.

### 3단계 — vite-plugin-rl `types` 옵션

플러그인이 `buildStart`/감시에서 `rlc types`를 실행한다 — TASK-033이 후속으로
예고한 것. README의 수동 체인 설명을 제거하고, 단독/플러그인 문서가 **같은
명령**을 가리키게 한다.

### 4단계 — 방출 동일성 계약 고정 + 문서 통일

같은 모듈을 `--rewrite-imports off`와 `js`/`ts`로 컴파일한 결과가 import
지정자 외에는 바이트 동일함을 `compile.rs` 계약 테스트로 고정한다.
README·`cli.md`에 "두 모드, 한 파이프라인" 절을 추가해 두 워크플로를 같은
표로 문서화한다.

### 후순위 — VSCode 확장 정렬

확장의 in-memory 선언 방출(`sidecar.ts`)이 `rlc types` 산출과 동일함을
테스트로 보장하거나, 장기적으로 확장이 `rlc types`를 직접 재사용한다.

## 의사결정

### 결정 1: 통일의 축은 "소스 불변 + 지정자 해석만 모드 차이"

- **상황**: "같은 방식"을 어느 수준까지 통일할지 정해야 했다.
- **검토한 대안**:
  - (a) 타입 경로만 통일 — 범위가 작지만, 소스 이식성 문제(현황 차이 1)가
    그대로 남아 "빌드를 만들어내는 방식"은 여전히 다르다.
  - (b) rlc가 자체 트랜스파일/번들까지 — tsc·번들러와 중복되는 거대한
    범위이고, "출력은 순수 TypeScript, 타입 에러는 tsc의 책임"이라는 설계
    계약과 충돌한다.
  - (c) 소스 형태를 통일하고 컴파일·타입 산출을 한 파이프라인으로 모으되,
    런타임 지정자 해석만 모드에 맡긴다.
- **선택과 근거**: (c). 통과 계약의 기존 예외(TASK-020) 하나로 성립하고 새
  예외가 필요 없다. 두 모드의 차이가 정확히 한 문장으로 정의된다.

### 결정 2: 단독 모드의 타입도 사이드카로 단일화

- **상황**: 단독 모드는 tsc 부산물 타입이 이미 공짜인데 사이드카로 바꿀
  것인가.
- **검토한 대안**: 두 경로 공존 유지 / 사이드카 단일화.
- **선택과 근거**: 단일화. 소스가 `"./x.rl"`을 import하는 순간 에디터와
  `tsc --noEmit` 모두 사이드카가 필요해지고, 정의 이동이 원본 `.rl`로 가는
  경험도 모드와 무관해진다. tsc 부산물 `.d.ts`는 라이브러리 배포용으로 여전히
  유효하며 그것은 방출 트리(1단계)의 몫으로 남긴다.

### 결정 3: `rlc types`가 tsc를 서브프로세스로 스폰한다

- **상황**: 선언 본문은 타입 추론이 필요해 tsc 없이 만들 수 없고, 지금 그
  오케스트레이션이 사용자(tsconfig.types.json)와 확장(자체 구현)에 흩어져
  있다.
- **검토한 대안**: 현상 유지(수동 체인) / node 헬퍼 스크립트를 별도 배포 /
  rlc가 tsc를 실행.
- **선택과 근거**: rlc가 실행. 플러그인이 rlc를 스폰하는 것과 대칭이고 배포물이
  늘지 않는다. rlc의 첫 외부 도구 의존이지만 `types` 모드에만 격리되고,
  tsc가 없으면 명확한 에러로 안내한다 (다른 모드는 영향 없음).

### 결정 4: 기본 `rlc <dir>` 수집 규칙은 바꾸지 않는다

- **상황**: `.ts` 수집을 기본 동작에 넣을지.
- **검토한 대안**: 기본 동작 변경(단순하지만 기존 사용자의 출력이 갑자기
  늘어난다) / build 모드에서만 확장.
- **선택과 근거**: build 모드에서만. 기존 워크플로 호환성을 지킨다.

## 리스크 / 열린 질문

- **tsc 스폰**: Windows(`tsc.cmd`), 모노레포에서의 tsc 위치, 버전 차이 —
  `--tsc` 옵션과 명확한 진단으로 흡수한다.
- **선언 방출 성능**: 전체 트리 방출은 느릴 수 있다 — watch에서는 변경분 +
  importer만 재방출한다.
- **`@rl/std` 소비 측 타입 해석**: `.rl-types/rl.d.ts` + tsconfig `paths`
  매핑이 필요 — 2단계에서 스니펫 안내로 시작하고, 자동화 여부는 열린 질문.
- **`.ts` 간 지정자**(`./util.js` 등): 재작성은 `.rl` 지정자만 다루므로 방출
  트리에서 그대로 유지되어 영향 없음.
