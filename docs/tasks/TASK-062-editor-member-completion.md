# TASK-062: 표준 라이브러리 메서드가 자동완성에 안 나오는 문제

- **상태**: 완료
- **시작일**: 2026-08-18
- **완료일**: 2026-08-18
- **커밋**: —

## 목적

사용자 보고 두 건:

1. `Result.`을 치면 `Ok`/`Err`만 나오고 `map`/`andThen`/`unwrapOr` 같은
   표준 라이브러리 콤비네이터가 하나도 안 나온다.
2. `n |> .toString()`에서 `.`을 친 순간 `toString`이 자동완성되지 않는다
   (`n`의 타입은 제대로 추론되는데도).

둘 다 "rl이 기본으로 제공하는 것들이 에디터에서 타입 추론되지 않는다"는
같은 증상의 다른 얼굴이다. 원인을 규명하고 언어 서버에서 고친다.

## 범위

- 포함: 언어 서버(`editors/vscode/server`)의 완성 경로 수정 — `Enum.` 멤버
  완성 병합, 완성 항목 resolve(타입 시그니처·JSDoc), 시그니처 헬프 추가,
  입력 중인 `.`을 위한 프로브 컴파일. LSP 왕복 회귀 테스트, 확장 README 갱신.
- 제외: 컴파일러(`src/`) 변경. 방출 코드·`--emit-map`·`--types`는 이번에도
  정상으로 확인됐다(아래 결정 1). 언어 표면이 그대로이므로
  `docs/reference/`는 갱신 대상이 아니다.

## 의사결정

### 결정 1: 먼저 "컴파일러인가 에디터인가"를 측정으로 가른다 (TASK-055 선례)

- **상황**: "타입 추론이 안 된다"는 보고는 방출 코드 문제일 수도, 에디터
  문제일 수도 있다. 방출 코드 문제라면 설계 계약 2번 위반이라 우선순위가
  완전히 달라진다.
- **검토한 대안**: (A) 서버 코드를 읽고 추정한다. (B) 언어 서비스 계층
  (`TsProject`)을 직접 구동해 TS가 무엇을 아는지 실측한다.
- **선택과 근거**: (B). `Result.` 위치에서 `TsProject.completionsAt`을
  직접 호출하니 25개 멤버(`andThen`…`unwrapOrP`)가 전부 나왔다. 즉 타입
  해석은 정상이고, **서버가 그 답을 버리고 있었다**는 것이 측정으로 확정됐다.

### 결정 2: `Enum.` 완성은 "생성자 대신"이 아니라 "생성자 + TS 멤버"

- **상황**: `server.ts`의 완성 처리는 `Enum.` 멤버 접근을 감지하면
  `return e.cases.map(constructorItem)` — 케이스 생성자만 돌려주고 TS
  위임 결과를 통째로 버렸다. `Result`/`Option`은 rl 내장 enum이면서 동시에
  표준 라이브러리의 값(콤비네이터가 달린 객체)이라, 이 분기가 곧
  "콤비네이터 전부 숨김"이 된다.
- **검토한 대안**:
  - (A) 내장 enum일 때만 TS 결과를 합친다 — 사용자가 선언한 rl enum도
    컴파일되면 생성자 객체이므로 구분할 이유가 없고, 분기만 늘어난다.
  - (B) 항상 합치고 라벨 중복은 rl 항목 우선으로 제거한다. rl 항목은 케이스
    시그니처와 필드 탭스톱 스니펫을 갖고 있어 TS의 같은 이름 항목보다 낫다.
- **선택과 근거**: (B). 정렬은 기존 규칙(rl 항목 `0`, TS 항목 `2`)을 그대로
  써서 생성자가 위에 오고 콤비네이터가 뒤따른다. 확인: LSP 왕복 테스트에서
  `Result.` → `Ok, Err, andThen, …, unwrapOrP` 25개.

### 결정 3: 항목의 타입은 eager가 아니라 `completionItem/resolve`로

- **상황**: 병합만 하면 목록에 이름만 뜨고 타입이 안 보인다. 보고의 절반은
  "타입이 안 보인다"이므로 시그니처를 실어야 한다.
- **검토한 대안**: (A) 목록을 만들 때 전 항목의 상세를 채운다 — 키 입력마다
  타입의 모든 멤버를 검사하게 되어 비싸다. (B) LSP resolve 단계에서 사용자가
  강조한 항목 하나만 `getCompletionEntryDetails`로 채운다(에디터가 하는 방식).
- **선택과 근거**: (B). 서버 capability에 `resolveProvider: true`를 켜고,
  각 TS 항목에 (문서 URI·원본 오프셋·엔트리 이름/source/data)를 실어 보낸 뒤
  resolve에서 되받는다. 확인: `map` 항목이
  `(property) map: <T, E, U>(r: Result<T, E>, f: (value: T) => U) => Result<U, E>`
  와 JSDoc으로 채워진다.

### 결정 4: 시그니처 헬프를 새로 추가한다

- **상황**: 서버에 `signatureHelpProvider` 자체가 없어서 `Result.map(`을
  쓰는 동안 파라미터 타입이 전혀 보이지 않았다. 콤비네이터는 인자가 곧
  타입 정보라 완성만으로는 반쪽이다.
- **검토한 대안**: (A) 이번 범위 밖으로 미룬다. (B) TS 언어 서비스에 그대로
  위임한다 — 이미 가상 문서 위에서 동작하므로 match 암·파이프라인 안에서도
  맞는 답이 나온다.
- **선택과 근거**: (B). 위임이라 새로 구현할 규칙이 없고, 파라미터 라벨은
  LSP의 `[start, end]` 오프셋 형태로 만들어 활성 파라미터가 정확히
  강조되게 했다.

### 결정 5: 입력 중인 `.`은 "프로브 컴파일"로 푼다

- **상황**: `n |> .`에서 `.`을 친 순간이 곧 완성 요청 시점인데, 그 버퍼는
  멤버가 없는 미완성 파이프라인이다. `--emit-map`은 이것을 **에러가 아니라
  원문 그대로 통과**시키므로 언어 서비스는 raw rl 텍스트를 보게 되고,
  `|>`에서 파싱이 무너져 멤버가 0개다. 에디터는 `.` 시점의 빈 목록을
  캐시하므로 그 뒤로도 안 나온다. (실측: raw 0개 / 방출물 6개)
- **검토한 대안**:
  - (A) 미완성 버퍼에도 가상 문서를 유지(직전 성공본 재사용) — 오프셋이
    어긋나 엉뚱한 위치의 멤버를 답한다.
  - (B) 서버가 파이프라인 디슈가를 직접 텍스트로 흉내낸다 — head 경계 추적
    같은 컴파일러 규칙을 에디터에 재구현하게 되어 TASK-050의 방침
    (에디터는 rl 문법을 다시 구현하지 않는다)에 정면으로 어긋난다.
  - (C) 커서에 자리표시 식별자를 끼운 **프로브 소스**를 컴파일한다.
    `x |> .$rl_probe`는 온전한 메서드 스텝이라 컴파일러가 평소대로 방출하고,
    자리표시자의 매핑된 위치가 곧 "파이프 값의 멤버"를 묻는 자리다.
    디슈가는 여전히 컴파일러가 한다.
- **선택과 근거**: (C). 확인: `n |> .` → `toFixed`/`toString`/`toPrecision`,
  `r |> Result.mapP(...) |> .` → 파이프 값(`Result`)의 멤버.

### 결정 6: 프로브 발동 조건은 "가상 문서 없음"이 아니라 "멤버 답이 아님"

- **상황**: 처음엔 "버퍼가 컴파일되지 않았을 때"를 조건으로 잡았는데,
  `--emit-map`이 미완성 파이프라인을 통과시키므로 **가상 문서는 존재한다**
  (내용이 원문일 뿐). 조건이 영영 참이 되지 않는다. 다음으로 "위임 결과가
  빈 목록일 때"로 잡았더니 이번엔 `x |> n.`이 새어 나갔다 — TS가 빈손이
  아니라 **전역 스코프 1008개**로 답했기 때문이다(이슈 4).
- **검토한 대안**: (A) 방출물과 원문이 같은지 비교 — 통과 계약상 정상적으로
  같은 파일(순수 TS)도 많아 오탐이다. (B) 빈 목록만 신호로 삼는다 — 위처럼
  전역 스코프 답을 거르지 못한다. (C) TS `CompletionInfo.isMemberCompletion`
  을 그대로 쓴다 — 멤버 자리에서 "멤버 완성이 아닌 답"은 정의상 쓸모가 없다.
- **선택과 근거**: (C). 멤버 자리(`.` 뒤)에서는 ① 멤버 답이면 그대로,
  ② 아니면 프로브를 만들고, ③ 프로브 답도 멤버가 아니면 **빈 목록**을
  돌려준다(전역 노이즈를 보여주느니 아무것도 안 보여준다). raw 텍스트로도
  멤버 파싱이 되는 자리(`x |> Result.` — 실측 25개)는 프로브 없이 답이
  나가므로 추가 컴파일도 없다.

### 결정 7: 프로브 텍스트는 그 질의 동안에만 서빙한다

- **상황**: 프로브는 사용자가 쓰지 않은 텍스트다. 이것이 진단 경로로 새면
  없는 에러를 보고하게 되어 에러 계층 계약(rl 에러는 rlc, 타입 에러는 원본
  위치)이 깨진다.
- **검토한 대안**: (A) 프로브를 가상 문서 맵에 넣는다 — 진단이 같은 맵을
  읽으므로 오염된다. (B) 언어 서비스가 파일 텍스트를 읽을 때만 끼어드는
  별도 슬롯을 두고, 동기 호출을 감싸는 동안에만 설치한다(`withProbe`).
- **선택과 근거**: (B). 설치와 해제 사이에 `await`이 없으므로 다른 요청이
  프로브 상태를 볼 수 없다. resolve만 예외적으로 직전 프로브를 다시 설치해
  같은 텍스트·같은 위치에서 상세를 얻는다(버전이 안 맞으면 그냥 포기).

### 결정 8: 프로브 컴파일은 버퍼와 다른 임시 파일 이름을 쓴다

- **상황**: `runEmitMap`은 넘겨받은 docName의 해시로 임시 파일 경로를
  만든다. 프로브가 버퍼와 같은 이름을 쓰면 진단 디바운스의 컴파일과 같은
  파일에 서로 덮어쓰는 경쟁이 생긴다.
- **검토한 대안**: (A) 그대로 쓰고 경쟁을 감수 — 드물지만 잘못된 완성이
  나올 수 있고 재현이 어렵다. (B) `<파일>.probe`를 docName으로 넘긴다.
- **선택과 근거**: (B). `--emit-map`은 모듈 해석을 하지 않으므로 docName은
  임시 파일 이름 외에 영향이 없고, 방출물은 여전히 실제 경로로 서빙된다.

### 결정 9: 멤버 접근 자리에서는 enum 이름·키워드 스니펫을 빼다

- **상황**: `|> .`은 앞에 식별자가 없어 "일반 위치" 분기로 떨어지는데, 그
  분기는 rl enum 이름과 `enum`/`match`/`try`/`let-else` 스니펫을 먼저
  붙인다. LSP 왕복으로 보니 실제로 `Option, Result, enum, match, try,
  let-else`가 멤버보다 위에 떴다.
- **검토한 대안**: (A) 정렬만 뒤로 민다 — 여전히 목록에 있고, 멤버 자리에
  `match` 스니펫이 있을 이유가 없다. (B) 커서 앞이 `.`이면 멤버만 답한다.
- **선택과 근거**: (B). `.` 뒤는 정의상 멤버 자리다.

### 결정 10: 프로브 구성은 별도 모듈로 빼서 테스트 가능하게

- **상황**: 버그는 `server.ts`에 있는데 이 파일은 임포트만으로 LSP 연결을
  열어 단위 테스트가 불가능하다.
- **검토한 대안**: (A) 서버 안에 두고 테스트는 포기 — 이번 회귀를 지켜줄
  테스트가 없다. (B) 순수한 부분(자리표시자 삽입 + 오프셋 매핑)을
  `probe.ts`로 빼고, 서버는 컴파일러 구동·서빙만 맡는다. 추가로 서버를
  `--stdio`로 띄워 LSP로 직접 묻는 왕복 테스트를 만든다.
- **선택과 근거**: (B) 둘 다. `probe.ts`는 주입된 emit 함수로 테스트되고,
  `server.test.ts`는 보고된 증상 그대로(`Result.` / `|> .`)를 에디터가 받는
  형태로 검증한다 — 지금까지 `server.ts`를 덮는 테스트가 하나도 없었다.

## 이슈 및 해결

### 이슈 1: 프로브 발동 조건이 영영 참이 되지 않았다

- **증상**: 처음 구현한 `probeFor`는 "가상 문서가 없을 때"만 프로브를
  만들도록 했는데, 실제로는 한 번도 발동하지 않는다.
- **원인**: `rlc --emit-map`은 미완성 파이프라인(`x |> .`)을 에러로 보지
  않고 파일을 그대로 통과시킨다(`--emit-map`은 parse+emit만 한다). 그래서
  `refreshVirtual`이 "성공"으로 가상 문서를 저장한다 — 내용이 원문일 뿐.
- **해결**: 조건을 "위임 결과가 빈 목록일 때"로 바꿨다(결정 6). 부수 효과로
  raw 텍스트로도 답이 나오는 자리에서는 프로브 컴파일이 아예 돌지 않는다.

### 이슈 2: match 암의 트레일링 `.`은 프로브가 필요 없었다

- **증상**: `Circle(radius) => radius.,`에서 "raw는 빈 목록"을 기대한
  테스트가 실패했다(실제로는 `toFixed` 등이 나왔다).
- **원인**: 암 본문의 `radius.`는 구조 파싱이 성공해 버퍼가 그대로
  컴파일된다 — 즉 가상 문서가 진짜 방출물이고 일반 경로가 이미 답한다.
  파이프라인만 "멤버가 없으면 스텝 자체가 미완성"이라 특별했다.
- **해결**: 테스트를 사실에 맞게 고쳤다(일반 경로가 답하고, 프로브를 써도
  같은 답). 코드 변경은 없다.

### 이슈 3: 멤버 자리에 rl 스니펫이 섞였다

- **증상**: LSP 왕복에서 `|> .` 완성 목록이
  `Option, Result, enum, match, try, let-else, toExponential, …`.
- **원인**: `|> .`은 점 앞에 식별자가 없어 `memberAccessAt`이 null을 주고,
  "일반 위치" 분기(enum 이름 + 키워드 스니펫 + TS 목록)로 떨어진다.
- **해결**: 커서 앞이 `.`이면 멤버만 답하도록 분기를 추가했다(결정 9).

### 이슈 4: `x |> n.`이 전역 스코프 1008개를 완성으로 내놨다

- **증상**: LSP 왕복 점검에서 `n |> n.`의 완성 목록이
  `$rl_ap, n, s, AbortController, … (1008개)` — 멤버가 아니라 스코프의 모든
  이름이고, 컴파일러가 방출하는 헬퍼 `$rl_ap`까지 노출됐다.
- **원인**: `|>`에서 회복하며 TS 파서가 점을 잃고 그 자리를 **식 시작
  위치**로 판단한다. 답이 비어 있지 않으니 프로브 조건("빈 목록")이 성립하지
  않아 그대로 나갔다.
- **해결**: `completionsAt`이 `CompletionInfo.isMemberCompletion`을 함께
  돌려주게 하고, 멤버 자리에서는 멤버 답만 채택한다(결정 6). 회귀 테스트로
  `$rl_ap`·`AbortController`가 목록에 없음을 확인한다.
