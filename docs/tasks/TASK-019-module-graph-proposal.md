# TASK-019: 모듈 그래프 설계 제안

- **상태**: 완료
- **시작일**: 2026-08-17
- **완료일**: 2026-08-17
- **커밋**: ec1c9e6

## 목적

rlc가 파일 하나를 파일 하나로만 컴파일하기 때문에 생기는 세 가지 제약 —
`.rl`끼리 import 불가, 파일 단위 소진성 검사, 파일 단위 정의 이동 — 이
사용자에게 각각 다른 불편으로 드러나고 있다. 원인이 하나이므로 하나의 설계
제안으로 묶어 정리하고, 결정해야 할 지점을 명시한다.

## 범위

- 포함: `docs/design/module-graph.md` 작성 — 문제 정의, 3단계 구현 경로,
  결정이 필요한 지점 5개, 범위 밖 항목 명시.
- 제외: 구현. 이 태스크는 제안 문서까지다. 각 단계는 결정이 내려진 뒤
  별도 태스크로 등록한다.
- 제외: 타입 검사 도입. rl의 에러 계층 분리 계약(tsc의 책임)은 유지한다.

## 의사결정

### 결정 1: 세 증상을 하나의 제안 문서로 묶는다

- **상황**: 사용자는 예제 프로젝트(`rl-calc`)를 만들다가 세 가지를 각각
  발견했다 — `.rl` import가 안 되는 것, enum 선언과 match를 같은 파일에
  억지로 묶어야 하는 것, 언어 서버에서 F12가 다른 파일로 가지 않는 것.
  이를 세 태스크로 쪼갤지 하나로 볼지 정해야 했다.
- **검토한 대안**:
  - 각각 별도 태스크: 증상별로 착수 시점을 고를 수 있지만, 셋 다 "모듈
    그래프 없음"이라는 같은 원인을 각자 우회하게 되어 설계가 갈라진다.
  - 하나의 제안으로 통합: 원인을 한 번만 해결한다. 대신 문서가 커지고
    착수 단위가 무거워진다.
- **선택과 근거**: 통합. 세 증상 모두 "rlc가 import 지정자를 읽지 않는다"로
  환원된다는 것을 확인했다 — `parser.rl`에서 `.rl` import를 컴파일해
  방출물에 지정자가 그대로 남는 것(`TS2307`), `language.md §3.6`의 파일
  단위 명시, `editors/vscode/server/src/analysis.ts`의 `parseEnums(src,
  masked)` 시그니처가 문서 하나만 받는 것. 착수 단위 문제는 문서 안에서
  3단계로 쪼개 해결했다.

### 결정 2: 제안 문서를 `docs/design/`에 두고 규범 문서와 구분한다

- **상황**: `docs/design/`에는 규범 문서(`compiler-architecture.md`)와 제안
  문서(`pipeline-operator.md`)가 섞여 있다. 새 문서가 구현되지 않은 제안임을
  독자가 오해하지 않아야 한다.
- **검토한 대안**: 별도 `docs/proposals/` 신설 / 기존 위치에 두되 문서
  첫머리에 상태를 명시.
- **선택과 근거**: 후자. `pipeline-operator.md`(TASK-013)가 이미 같은 방식의
  선례이므로 디렉터리를 늘리지 않았다. 문서 첫 문단에 "이 문서는 제안이다,
  규범 문서가 아니다"를 명시하고 규범 문서로 링크를 걸었다.

### 결정 3: 구현 경로를 3단계로 쪼갠다

- **상황**: "모듈 그래프 도입"은 한 번에 하기에 크고, 어디까지 해야 어떤
  증상이 풀리는지가 불명확했다.
- **검토한 대안**: 단일 변경(그래프 + 소진성 + 심볼 API 동시) / 단계 분리.
- **선택과 근거**: 단계 분리. 1단계(지정자 재작성)는 참조 파일을 열지 않으므로
  현재의 파일 단위 파이프라인을 유지한 채 codegen에서만 처리할 수 있고, 그
  자체로 "소스가 소스를 가리킨다"는 가치를 낸다. 2단계에서만 컴파일 단위가
  파일에서 그래프로 바뀐다. 3단계는 2단계 산출물(선언 테이블)을 외부에
  노출하는 것뿐이다. 각 단계가 독립적으로 배포 가능하다.

### 결정 4: 방출 지정자의 형태는 열린 결정으로 남긴다

- **상황**: 1단계에서 `.rl`을 무엇으로 바꿀지 정해야 한다.
- **검토한 대안**: `.js` 고정 / 확장자 없음 고정 / 플래그 / `tsconfig.json`
  자동 판별.
- **선택과 근거**: 결정하지 않고 선택지와 근거를 문서에 남겼다. 올바른 값이
  rl이 아니라 **소비 측 `moduleResolution`**에 달려 있기 때문이다. 확인한
  사실만 기록했다 (tsc 5.9.3):
  - `nodenext` + 확장자 없음 → Node ESM 해석 실패
  - `bundler` + 확장자 없음 → 통과 (exit 0)
  - `"./x.ts"` → `TS5097`, `allowImportingTsExtensions` 활성화 시 `TS5096`으로
    emit 불가
  자동 판별은 rlc가 TypeScript 설정을 해석하기 시작한다는 뜻이라 비용이
  크다는 점도 함께 적었다.

## 이슈 및 해결

### 이슈 1: 계약 1 위반이라는 초기 판단이 과했다

- **증상**: 지정자 재작성이 절대 불변 원칙 1("모든 유효한 TypeScript 파일은
  바이트 그대로 통과")을 깨므로 옵트인 플래그가 필수라고 결론지었다.
- **원인**: "유효한 TS 파일이 `.rl` 지정자를 가질 수 있다"를 검증 없이
  전제했다. 실제로는 tsc가 `.rl` 지정자를 해석하지 못하므로(`TS2307`)
  번들러에 `.rl` 로더를 붙인 프로젝트에서만 유효한 TS이고, 그 로더는 rl
  자신이다.
- **해결**: 문서에서는 "실질적으로 존재하기 어려운 예외"로 낮춰 적고,
  기본 동작으로 넣을지 옵트인으로 둘지를 열린 결정으로 남겼다.
