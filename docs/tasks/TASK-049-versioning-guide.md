## 의사결정

### 결정 1: TypeScript식 "릴리스 단위 버저닝"을 채택한다

- **상황**: 작업(태스크)마다 버전을 올릴지, 릴리스를 자를 때만 올릴지 규칙이
  없어 버전 인플레이션 우려가 있었다. 프로젝트는 아직 정식 출시 전(0.x)이다.
- **검토한 대안**:
  - A. 태스크/기능마다 버전 올림 — 추적은 쉽지만 출시 전에 버전이 무의미하게
    치솟는다(현재 48개 태스크 완료 → 이 방식이면 이미 0.48+).
  - B. 엄격한 semver(변경 유형별 자동 판정) — 0.x 구간에서는 semver 자체가
    "언제든 깨질 수 있음"만 뜻해 실익이 적고, 판정 비용만 든다.
  - C. TypeScript식 릴리스 트레인 — 버전은 "릴리스를 자른다"는 명시적 결정이
    있을 때만 올린다. TypeScript는 커밋/기능마다 버전을 올리지 않고 여러
    변경을 feature release(minor)로 묶으며, patch는 릴리스된 버전의 심각한
    수정에만 쓴다. 나이틀리는 릴리스 버전을 건드리지 않고 `-dev` 스탬프로
    배포한다.
- **선택과 근거**: C. 이 저장소의 실제 이력과도 일치한다 — `git log -L`로
  확인한 결과 Cargo.toml 버전은 대규모 릴리스성 변경에서만 두 번
  (0.2.0 Rust 재작성, 0.3.0 enum 통합) 올랐고, 48개 태스크 대부분은 버전을
  건드리지 않았다. npm 패키지(`npm/rl-lang`)도 이미 저장소에서 `0.0.0-dev`로
  두고 배포 시 `stamp-version.mjs`로 스탬프하는 TypeScript 나이틀리와 같은
  구조다(TASK-048).

### 결정 2: 기준 버전은 Cargo.toml 하나, 부속 패키지는 각자 배포 시점에만

- **상황**: 버전 선언이 다섯 곳에 있다 — `Cargo.toml`(0.3.0),
  `npm/rl-lang/package.json`(0.0.0-dev, 배포 시 스탬프),
  `editors/vscode/{,client/,server/}package.json`(0.1.0),
  `integrations/unplugin/package.json`(0.1.0). 전부 동기화할지 결정 필요.
- **검토한 대안**: 전 패키지 버전 동기화(lockstep) vs 컴파일러 버전만 기준으로
  두고 부속 패키지는 독립.
- **선택과 근거**: 컴파일러(`Cargo.toml`)를 기준 버전으로 하고 부속 패키지는
  독립 버전 유지. npm 메인 패키지는 스탬프 방식이라 이미 Cargo.toml을
  따라가고, vscode 확장·unplugin은 릴리스 주기가 다르므로 lockstep은 불필요한
  버전 올림만 만든다.
